# Core 执行模型设计书

> 定位：受众 = 维护者；状态 = active

---

## 一、核心原则

### 1.1 唯一执行模型

Core 只有一种执行语义：HDFG。

程序员编写的所有代码，经语义 IR 翻译后，构成一张有向图。图的拓扑结构承载了程序的执行语义（依赖、迭代、并发结构）：

| 图结构 | 承载的执行语义 |
|--------|----------|
| 有向无环图（DAG） | 依赖偏序——无反馈，确定性 |
| 带反馈环的静态图 | 迭代语义——循环结构，region 表达迭代与终止 |
| 动态图（运行时创建/销毁节点） | 并发语义——节点创建、生命周期动态管理 |

程序员不需要声明"模式"——代码写了什么，图就反映什么。执行方式（串行/并行/调度策略）由部署配置决定，图语义不变。

### 1.2 部署配置原则

物理世界的约束——内存是否可动态分配、是否多核、是否有操作系统——不属于程序的执行语义，而属于部署目标的属性。

这些属性在部署配置文件中声明，由编译器据此检查代码兼容性并生成对应代码。代码不变，部署配置可变。

I/O 系统调用、时间源等物理实现同理：程序只见语义接口——I/O 语义是流变换（转导器：(输入流) → (输出流)），时钟语义是单调时间序；底层系统调用由后端实现按部署目标隔离，不进入程序语义。

### 1.3 渐进式能力解锁

Core 的语法特性按图结构复杂度分为三个层级：

| 层级 | 语法特性 | 产生的图结构 | 心智模型 |
|------|----------|--------------|----------|
| 基础 | 变量、函数、分支、循环（for） | DAG | 顺序执行 |
| 中级 | loop、recv | 带反馈环的静态图 | 循环调度 |
| 高级 | flow、go、yield、await | 动态图 | 并发，有时间片或 OS 线程 |

初学者从基础层级起步，图是 DAG，执行顺序与文本顺序一致。引入并发语法特性后，图的拓扑随之复杂化——无需声明"模式切换"。

## 二、图承载执行语义

### 2.1 DAG：天然的教学与调试执行

```core
fn add(x: int, y: int) -> int {
    return x + y;
}

fn main() {
    a := 5;
    b := 3;
    c := add(a, b);
    println(c);
}
```

生成的图是无环的。执行器按拓扑序串行走节点。
单步调试即顺序走节点，变量值完全可预测。

DAG 结构本身适合教学场景——无需额外的模式声明。

### 2.2 静态循环图：有节奏的循环调度

```core
fn main() {
    data := [1, 2, 3, 4, 5];
    loop {
        if data.is_empty() { break; }
        item := data.pop();
        println(item);
    }
}
```

图包含循环 region（loop/for 结构节点，含子区域；region 边界表达迭代与终止依赖）。
执行器按迭代节奏执行。仍然可串行模拟，可单步跟踪循环迭代。

### 2.3 动态图：并发与自适应

```core
flow worker(id: int) -> int {
    loop {
        yield compute(id);
    }
}

fn main() {
    w1 := go worker(1);
    w2 := go worker(2);
    loop {
        v1 := await w1;
        v2 := await w2;
        println(v1 + v2);
    }
}
```

图在运行时动态扩展：go 创建新节点，yield 暂停当前节点并输出值。有 OS 时每个 go 对应一个线程，无 OS 时 Core 提供抢占式调度器（时间片轮转）。

## 三、资源分配：由部署配置声明

### 3.1 代码不规定分配策略

Core 代码只描述计算的逻辑和数据的结构，不规定内存从哪来、怎么分配。
语义 IR 保留数据的类型和边界信息（包括编译期已知的上限），但不固定分配策略。

### 3.2 部署配置描述目标平台能力

```toml
[deploy.mcu]
target = "cortex-m4"
allocation = "static"          # 禁止动态分配
max_memory = "256KB"

[deploy.server]
target = "x86-64-linux"
allocation = "dynamic"         # 允许动态分配
```

编译时：

- 目标为 mcu：编译器检查所有可变大小数据结构是否已有编译期确定的上限。若无法确定，拒绝编译并给出明确错误。
- 目标为 server：编译器生成使用目标平台分配器的代码，允许运行时决定大小。

程序员仍然只写一份代码。如果这份代码能在静态分配世界运行，它必须足够保守；如果只能在动态分配世界运行，它就对部署环境有要求。

### 3.3 资源配额：运行时可选策略

资源配额（CPU 时间片、内存上限、I/O 速率）不属于程序逻辑，属于运营策略——I/O 速率配额约束的是后端流传输的物理速率，不改变程序语义（流变换）。
在部署配置中可选声明：

```toml
[deploy.server.quotas.flow.worker]
max_memory = "10MB"
cpu_budget = "5ms"
```

不声明即无限制。代码不变。

## 四、时间语义：由部署上下文决定

时钟的语义是单调时间序（数学）：程序代码中不区分"零时间""物理实时""仿真时间"，只要求时间序单调。

时间是一个可选的外部输入源——时间源由部署上下文与后端实现决定（平台桥提供 now_monotonic/sleep_ms 语义接口，clock_gettime/nanosleep 等系统调用隔离在后端实现）：

- 裸机或实时 OS：硬件时钟提供物理时间，调度器可据此满足 deadline。
- 普通 OS：系统时钟提供逻辑时间，保证事件偏序。
- 仿真环境：仿真器提供可控时间，可加速、暂停、回放。

部署配置决定时间源，而非代码决定。程序语义始终是单调时间序，不绑定具体时间源。

## 五、调度器

### 5.1 原则

Core 不自己实现调度器——除非没有操作系统。

```
有 OS：    用线程，OS 调度，Core 不需要 scheduler
无 OS：    Core 自己管，时间片轮转，抢占式
```

部署配置决定，代码不决定：

```toml
[deploy.linux]
scheduler = "os"              # 用线程，OS 调度

[deploy.bare_metal]
scheduler = "preemptive:10ms" # Core 自己调度，10ms 时间片

[deploy.wasm]
scheduler = "preemptive:5ms"  # 同
```

### 5.2 有 OS 环境

`go fn()` 创建一个新线程。yield、await 等操作在线程内进行，不涉及 Core 的调度器。OS 负责时间片分配和上下文切换。

### 5.3 无 OS 环境

Core 提供最小化的抢占式调度器。和 OS 线程调度相同——基于时间片中断，而不是协作式 yield。

```core
flow worker(id: int) {
    loop {
        data := recv(input);
        result := compute(data);
        yield result;
    }
}

w1 := go worker(1);   // 新节点，加入就绪队列
w2 := go worker(2);   // 新节点，加入就绪队列
```

调度器循环：

```
1. 时钟中断（或模拟 tick）→ 当前节点时间片到
2. 保存节点上下文
3. 选择下一个就绪节点（round-robin / work-stealing）
4. 恢复上下文，继续执行
5. 节点 yield/await 时主动让出，不等待时间片
```

### 5.4 默认策略

有 OS 时全部走 OS 线程，无 OS 时走抢占式。不提供协作式选项。

## 六、静态图与动态图

Core 区分静态图和动态图，但这不是模式——它们是图的两个形态：

### 6.1 静态图

编译期已知所有节点和边。
类型：DAG、带循环的静态图。
执行：拓扑序、循环调度。
用途：计算、控制逻辑、无动态创建的流。

### 6.2 动态图

运行时创建/销毁节点、重连边。
类型：带有 go、动态 select 的图。
执行：动态节点生命周期管理。
用途：长期服务、自适应系统、热升级。

初学者从静态 DAG 起步，逐步解锁动态图特性。这不需要"切换模式"，只是使用更多的语言能力。

## 七、代码与部署配置分离

```core
fn compute(x: int) -> int { x * 2 }

fn main() {
    result := compute(42);
    println(result);
}
```

这段代码：

- 在教学环境 → DAG，拓扑序解释执行，可单步、可回退
- 在桌面 → AOT 编译，直接原生执行
- 在嵌入式中 → 静态分配，零运行时
- 在分布式集群 → 可远程部署 compute

代码不改。图的语义相同。部署配置不同。

## 八、与传统做法的对比

| 传统做法 | Core |
|----------|------|
| 代码中声明模式（#[mode(release)]） | 代码无模式概念 |
| 不同模式影响语义或行为 | 图语义唯一 |
| 切换模式可能引入 bug | 部署配置不影响程序正确性 |
| 模式数量膨胀 | 无模式分类 |

Core 只有一种执行语义：图。
图结构由代码决定，物理约束由部署配置声明，执行策略由编译器自动选择。

---

## 九、结论

Core 的执行模型可以总结为一句话：代码生成图结构，图承载执行语义，执行方式由部署配置决定。拓扑简单则执行简单，拓扑复杂则执行复杂——不需要人为命名任何一种"模式"。
