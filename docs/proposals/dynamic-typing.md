# Core 动态类型

> 定位：受众 = 贡献者；状态 = proposal(讨论中)

## 设计原则

- **弱动态风格，编译器在图知道的范围内做到强动态的保证。**
- **动态值不是胖结构。** 图在 90% 的路径上知道确切类型，变量就是裸值，零开销。
- **全生命流图已知所有分支可能。** 没有"不确定"，只有"可能取值集合"，编译器为每种可能生成一条处理路径。

## 声明

```core
x : dyn = 42;       // 动态类型
x : dyn = "hello";  // 同一个变量，类型变了

y : int = 42;        // 静态类型，不能变
z : auto = 42;       // 自动推导，仍然是静态
```

`dyn` 是类型关键字，和 `int`、`string` 平级。

## 图上的表示

每个 `STORE(x: dyn)` 节点在当前路径上记录类型 tag。不同路径上 tag 不同时，编译器在汇合点为每种可能生成一条处理路径。

```core
if cond { x := "42"; }      // 路径 A: x 是 string
else    { x := 100; }       // 路径 B: x 是 int

y := x + 1;
// 编译器：
//   x 的全量可能：string | int
//   路径 A: string_to_int 后加法
//   路径 B: 直接加法
```

没有"运行时才知道"——编译器已知全量分支。

## 边界转换

编译器看图知道两边的类型，在边界自动插入转换代码。

```core
x := "42";
y := x + 1;
// 图：x 是 string，+1 需要 int
// 编译器：string_to_int 插在加法之前
// 运行时 x 全程是裸 string，没有装箱
```

```core
x := 42;
z := x + "hello";
// 图：x 是 int，"hello" 是 string
// int + string → int_to_string + 拼接
```

## 与静态类型的交互

| 静态←dyn | 编译器行为 |
|-----------|-----------|
| 图知道类型匹配 | 编译期决议，零开销 |
| 图知道类型可转 | 插自动转换代码 |
| 图知道不匹配且不可转 | 编译错误 |

## 方法调用

图全量已知所有分支的类型，为每种可能生成对应的调用路径。

```core
x : dyn = cond ? "hello" : 42;
x.len();
// 路径 A: string → 有 .len()，直接调
// 路径 B: int → 无 .len()，编译错误
// 全路径都有 → 编译期决议，零开销
// 部分路径有 → 编译错误（动态类型不隐藏不存在的方法）
```

动态类型不隐藏不存在的方法——任何路径上都没有的方法在编译期报错。

## 运行时表示

动态值在运行时没有统一包装。只有一种情况需要额外存储：

当编译器需要为同一个变量生成不同路径的代码时，为这个变量生成一个 `(tag, value)` 栈上对：

```core
x : dyn = cond ? 42 : "hello";
// 编译器：x 可能是 int 或 string
// x 在栈上是 { tag: int|string, value: 8字节 }
// 后续代码根据 tag 分派
```

这个开销不是全局的——只在图发现多路径歧义的那个变量上。单路径的 `dyn` 变量就是裸值，零开销。

## 滚动更新

热补丁（原子替换）是滚动更新的特例。滚动更新是新旧版本共存、流量逐渐迁移，Core 的子图边界天然支持：

### 声明

```core
@hotpatch(canary="5%") fn handle(x: dyn) -> dyn;
// 新版本先收 5% 流量

@hotpatch(rollout="50%") fn handle(x: dyn) -> dyn;
// 确认稳定后扩到 50%

@hotpatch(rollout="100%") fn handle(x: dyn) -> dyn;
// 全量

@hotpatch(drain="true") fn handle(x: dyn) -> dyn;
// 旧版本排水完成后回收
```

### 图上的实现

```
路由节点（由 @hotpatch 参数生成）：
    • 根据比例或请求属性选择子图
    • 旧子图和新子图同时存在
    • 排水：已有请求走完旧路径后，移除旧子图

子图的独立性天然保证：
    • v1 和 v2 的内部图互不干扰
    • v1 的指针不会泄露到 v2
    • 编译器各自验证，互不影响
```

### 需要的机制

| 机制 | Core 已有的基础 |
|------|---------------|
| 多版本子图共存 | 子图边界——每个版本是独立子图 |
| 流量路由 | 运行时路由节点（按比例/请求属性选择子图） |
| 排水 | 旧子图保留到请求完成，然后回收 |
| 回滚 | 路由比例退回旧版本 |

这比热补丁轻——不需要接口契约编译、不需要图链接器验证。滚动更新就是一个会按比例分流的路由节点，子图的隔离性是 HDFG 自带的。热补丁是 `rollout="100%"` 后 `drain="true"` 的特例。

## 当前状态

- **`dyn` 动态类型**：已实现（2026-07-30，PR #21）——声明、全路径推导、汇合点 `(tag, value)` 栈上对、边界自动转换
- **热补丁（@hotpatch）**：基础机制已实现（2026-07-29，PR #19）——`@hotpatch(ver=N)` 多版本签名校验 + IR_HOTPATCH_ROUTE 调用点路由 + SIGHUP 信号处理 + in_flight drain 追踪
- **滚动更新（canary/rollout/drain 参数化分流）**：本文档 §滚动更新 为设计态，**未实现**——当前 `@hotpatch` 是"版本切换"而非"按比例分流"；canary/rollout 等参数化流量路由待实现（子图边界隔离性已具备，缺的是路由节点的比例分流逻辑）
