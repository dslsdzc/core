# 状态版本与 TOCTOU 检查

## 概述

`check(x); use(x)` 之间，外部状态可能被其他进程、线程或硬件改变。检查和使用落在两个不同的状态版本上，就会产生 TOCTOU 问题。

本文定义状态版本模型、检查规则和 handle 身份绑定。目标是把 `open`、验证、操作三段绑定到同一个身份和同一个版本上。

## 设计原则

- 复用现有的 ENT 版本、存在区间和 state 边，不引入第二套版本机制。
- 外部对象是“无方法条目”，世界版本按定义不进图。
- 检查只证明图上可见的部分；外部代理的行为不能被证明，只能被声明或缩小。
- 未证明的义务不能不报错地消失。
- 不新增语言 primitive 或关键字；策略面放在领域库。

## 状态版本模型

| 面 | 现有表示 | 用途 |
|---|---|---|
| 版本身份 | ENT `(var_id, version)` | 判断两次访问是否同一版本 |
| 定值点 | ENT `def_nod` | 版本推进时换新的 `def_nod` |
| 存在区间 | ENT `[live_start, live_end)` | 版本在图上有效的窗口 |
| 无方法 | ENT `flags bit0` | 标记外部对象或不可重算的条目 |
| 顺序 | EDG `kind=1` | 副作用顺序约束 |

这些字段一个不改，一个不加。

## 外部状态进入图

外部状态通过四条通道进入图：

1. 观察：边界节点（extern、`unsafe`、syscall、MMIO）产出条目，并设置 `flags bit0`。
2. 身份：handle 值就是条目，身份等于产生它的图节点身份。
3. 变更：图内变更由 STORE 族节点表示；图外变更没有节点，这正是 TOCTOU 的对象。
4. 顺序：图内变更和观察之间的顺序由 `kind=1` state 边表示。

外部调用可以带 `mutates(κ)` 注解，κ 是身份键。未标注的 extern 或未知调用，保守视为“变更一切外部身份”。

## TOCTOU 检查

设 check 节点为 C，验证谓词 P 在身份 κ 的版本 `v(C)` 上成立。设 use 节点为 U，作用于身份 κ。U 合法需要同时满足三条：

- C1：`v(C)` 和 `v(U)` 是同一版本，并且 C 支配 U，或者 U 直接使用 C 的版本见证。
- C2：从 C 到 U 的状态路径上，没有 κ 的 mutator，并且 U 本身不是对 κ 的重观察。
- C3：κ 在存在区间内被声明为“外部代理不会推进它”，也就是独占或不可变。

C1 由类型引擎判定。C2 由 state 边可达性判定。C3 由治理层的 `kind=stability` 条目声明，条目需要主体、范围、理由、派生源和义务引用；字段缺失时拒绝装载。

三条缺一条，就落到后面的义务分级，不能不报错地通过。

## 版本分离

重新观察同一身份会产生新的边界节点、新的条目和新的 `def_nod`，因此 `v(U) ≠ v(C)`，C1 不成立。这就是 `check(x); use(x)` 的图形态。

版本分离本身不是错误。写后重读、重新验证是合法的。错误是：分离出新版本后，没有在新版本上重新 check 就直接 use。

| 模式 | 形态 | 结果 |
|---|---|---|
| P1 | `h = open(p); v = verify(h, P); op(v)` | 同一身份同一版本，prove |
| P2 | `v = observe(x); verify(v, P); use(v)` | 同一版本，prove；内容谓词可能需要稳定性声明 |
| P3 | `check(p); …; use(p)` | 两个版本，C1 不成立，enforce 或 reject |
| P4 | `v = verify(h, P); …; mutate(κ); …; op(v)` | 窗口内有变更，C2 不成立，enforce 或 reject |
| P5 | `check(p); …; use(p)`，窗口内无变更 | 仍有两个版本；重查不默认继承验证 |
| P6 | `write(h); v = observe(h); verify(v, P); use(v)` | 写后重读，新 check 落在新版本上，prove |

P5 的原则是：宁可要求重新验证，也不不报错地证明。两次读是否等价本身需要证明，而内容可能被写。

## Handle 身份绑定

接口形态：

```text
open(p, …)   -> Handle[κ]
verify(h, P) -> Verified[P, Handle[κ], v]
op(vh, …)    -> …
```

- `open` 是边界节点，做一次身份解析，产出条目。
- `verify` 把谓词 P 绑定到 `(κ, v)`。
- `op` 只接受 `Verified`，不接受 pathname。

因此 `op` 不存在“按名字重新解析”这个动作，身份绑定是构造出来的，不靠事后证明。

`Handle<R>` 是独立类型，不嵌入 `Path<R>`。转换点是 `bind(p: Path<R>) -> Handle<R>`。`bind` 是唯一的 check/use 边界，也是 C1 的判定对象。`bind` 的原子性由映射层提供，例如 fd、dirfd 或 `openat` 一类机制。

身份谓词和内容谓词分开处理：

- 身份谓词（存在、类型、属主、路径）由 handle 构造消解。
- 内容谓词（权限位、内容摘要、大小）不能靠 handle 消解，需要值绑定或 enforce。

## 与命名空间限制的分工

命名空间限制负责“名字到 capability 的构造单步且不可回退”。本文负责“capability 到资源身份的绑定是原子的”。

两族互不重新定义：限制不定义版本，本文不定义命名空间。映射层没有 handle 化能力时，高安全档只能 reject；有 handle 化能力时，symlink、mount、hardlink 一类解析身份由映射层强制。

## 义务分级

| 档 | 条件 | 处置 |
|---|---|---|
| 1 prove | C1、C2、C3 全部成立 | 零成本通过 |
| 2 enforce | C1 成立或可重建，C2 或 C3 不可证 | 在 use 前紧邻一次同身份观察和版本比对；不一致就失败关闭 |
| 3 proof-required | 需要“κ 独占或不可变”，但引擎不可判 | 要求用户或领域库提供稳定性 contract |
| 4 reject | 高安全档下 C1 不成立，且没有可执行的 enforce 通道 | 拒绝编译 |

每个判定结果必须落到四档之一，没有第五种“算了”。

enforce 的规则是：版本重校验必须紧邻 use，并且失败关闭。“检查后再用一个可能已经变化的东西”不是 enforcement，是 TOCTOU 的复现。

## 最小切片

第一版只做注解和判定，不改存储：

1. 身份键 κ 和 `mutates(κ)` 注解面，包括 handle 派生面和保守 extern 面。切片不写入磁盘。
2. 版本等价判定调用类型引擎的 `ty_equiv`。
3. 一个判定 pass：对每个 use 求 C1、C2、C3，输出四档分类和反例。
4. 检查：零产物变化；未启用注解时，现有程序不受影响。

策略注解的持久化以后放进 `.ccr` 的 POLICY 或 LABEL 段，随 R2 P4 的段位实现。不扩展 TYPE/IFACE 段，也不动 EDG 的保留 kind。

切片不改 stdlib，不做跨过程 κ 传播。

## 不包含

- 不新增语言 primitive 或关键字。
- 不把 TOCTOU 做成内建特判。
- 不重造版本机制。
- 不判定并发线程或 flow 之间的竞争；那属于 S-E。
- 不做 OS 内核内部的 TOCTOU。
- 不做平台 syscall 语义正确性。
- 不做 stdlib 的 handle 化。
- 不锁形状项语法。
