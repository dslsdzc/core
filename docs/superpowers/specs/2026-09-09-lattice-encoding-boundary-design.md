## 0. 背景与定位

### 0.1 起因

HIT M2 实施（表驱动发射收口）在 Task 3 停摆：branch 模板形态（spec 两步 cmp+jcc vs 旧发射器实际四原子 load+test+je+jmp）、ret 事件（裸 C3 vs 旧路径 IR_RETURN = 值序列+jmp→epilogue+ret_patch）连续撞出计划级矛盾。排查结论：**矛盾是症状**——模板在逐字节复刻一个本身经典形状的旧发射器。这暴露了更上层的问题：转换编码层（corearch）与经典计算机绑定太深。

### 0.2 定性（2026-09-09 用户确认）

1. **.ccr（格形态）大体成立**——图坐标 NOD + REG 嵌套 + ENT 存在结构，方向对，不推倒
2. **.ccr 局部不纯**——NOD 语义仍为 v5 变量槽指令（load/store 字节槽、变量 = 可寻址位置而非条目 × 版本）；ENT 恒空（存在结构 = 侧表，未成主干）；在「格不重新引入程序顺序」判据的边线上
3. **真正的病灶 = 转换编码这一层（corearch）**——结构把经典机形状硬写进转换器逻辑：槽→rbp 帧公式、寄存器分配、ABI 分派、tag/2L 编码选择、call/ret 控制栈、ELF；降低器（lower_to_core：IR → 槽操作 + 栈控制事件）同样经典形状化
4. **表驱动（HIT/M2）只数据化了最后 1 英寸**（指令字节），经典机绑定在转换器中段（帧/ABI/调用/降低）纹丝不动——本 spec 把实例化边界推到它该在的地方

### 0.3 本 spec 的权威用法

任何格式字段、模块、算法、计划任务，都可以被本 spec 的判据问四组问题（§1），按审计方法（§2）与契约条款（§3）判定归属。**裁决结果先于新工作**：M2/HIT 后续任务、corearch 重写、v7 方向、第二维护者的横向扩展，凡涉层归属者均须能回答「格语义对象 | 实例数据 | 实例算法 | 泄漏待归一」。

## 1. 判据完备化（可逐类判定的准则集）

四组判据从既有锚点推导。每组末尾给出**判定问题**——对任意对象可逐条作答；任何一条答「是泄漏侧」即进入 G4 类型学点名。

### G1 语义本体判据（缓存语义七条的判定形态）

锚点：`docs/memory-model.md` §一（值 = 配方 / 驱逐不变量 / 再生等价 / 边界公理 / 赋值 = 版本化 / 地址 = 映射 / 映射实例正确性）+ 无配方条目统一规则。

判定问题：

1. **配方性**：该对象有配方吗（可由 (产生它的图节点, 输入边) 再生）？驱逐它、保留配方，可观测语义变吗？
2. **赋值形态**：赋值表达为版本创建/失效/绑定移动，还是内存单元修改？
3. **位置形态**：位置语义 = (条目标识, 偏移)，还是字节地址？
4. **身份形态**：身份 = 产生节点（图节点身份），还是独立存储事实？
5. **边界形态**：无配方条目（边界/图内不可重算）是否按统一规则处理（不按范式枚举）？

### G2 层形状判据（格层形态的充分条件）

锚点：capability-lattice v4 §4.2（**格不重新引入程序顺序**——传统 IR/SSA/LLVM 本质仍是「另一种程序」，按执行路径组织；这是三层链成立的关键判据）、§4.5（规则封闭对象开放）、§4.6（无格承诺）。

判定问题：

1. **程序顺序**：该结构是否按执行路径组织（文件序/指令序 = 执行序）？若序仅为图的合法拓扑序列化（图语义完整可重建），判「序列化」，不判「程序顺序」——**判据是语义载体是否完整，不是文件是否线性**
2. **范式枚举**：规则/判定是否按范式枚举？层本体规则封闭（永不新建），对象开放（无界）
3. **条目泛型**：判定是否操作「条目」类别（位置 + 配方 + 存在）而不读值内容？
4. **最弱理论**：语义是否写在比具体格代数更弱的理论里（共存 = 对称关系即可，无传递性承诺）？

### G3 实例/参数判据（编码层内容的合法形态）

锚点：z-vision 三层映射链（编码 = 物理编码空间——把格编码成具体机器的地址、字节、指令、位模式；编码层绑定经典机 = 合法且必须）、capability-lattice §11.5（寄存器分配 = 缓存语义映射实例 = 已接纳先例）、§4.6（具体格代数 = 映射参数）、memory-model §二（区域/arena/字节权限 = 经典映射实例）。

判定问题：

1. **可换性**：换平台（目标机/范式实例）时该内容语义不动吗？动 = 映射参数/实例数据；不动 = 该内容属格层；「换不掉且硬编码在通用机制里」= 泄漏
2. **先例类推**：是否与「寄存器分配 = 缓存语义映射实例」同族（对缓存语义的机器侧资源决策）？同族 → 实例化处理，先例已接纳
3. **参数形态**：具体代数/组织（乘积格、ABI、帧序）是否作为映射参数存在，而非层本体承诺？

### G4 泄漏类型学（点名用分类）

经典绑定泄漏的四种形态——审计与契约条款引用此分类：

| 类 | 名称 | 定义 | 典型表现 |
|---|---|---|---|
| ① | 存储形状泄漏 | 变量 = 可寻址存储位置（帧槽/字节内存操作）进入格语义层 | load/store 字节槽、变量 = 内存单元、`&x` = 字节地址 |
| ② | 控制形状泄漏 | 经典控制流形状进入格语义层 | 函数 = 可调用子程序、标签/跳转、栈 call-ret、行式执行序 = 语义 |
| ③ | 编码选择泄漏 | 目标机编码选择固化进格格式/转换器通用机制 | tag 字节布局、2L 堆指针表示、jo 溢出链、imm 宽度选择 |
| ④ | 平台惯例泄漏 | 平台惯例出现于格层或转换器核心 | ABI 寄存器分派、参数栈序、ELF/rodata 布局、调用约定 |

判定规则：G1-G3 答「泄漏侧」的对象 → 归入 G4 类别点名；归入后按 §3 契约裁决去向（实例数据 / 实例算法 / 入口归一化）。

## 2. v6 审计裁决表

审计对象 = `.ccr` v6 格式的**设计语义**（以 `2026-09-05-lattice-ir-v6-format.md` 为基——v6 spec 自身明言若干妥协，见下）；实现现状差异单列注记（§2.6）。格式 = 逐成分 × 判据 → 裁决。

### 2.1 格式骨架（Header/段表/坐标体系）——格侧成立 ✅

- 段表组织/变长记录/字节宽 = **编码层事务**（v6 spec §7 开放点自认；G3-1：换编码空间可调）——不构成格层问题
- **坐标 = NOD id（图坐标）**（D1）：存在区间端点/region 边界/定值点全部以图节点序为坐标——与 .cir 同坐标系，兑现「图 = 唯一真相层」坐标承诺——**格侧成立**
- 版本化 v6-only、无转换工具：管线中间产物定位，OK

### 2.2 NOD（节点表 = 图事件 = 配方载体）——方向成立，语义带泄漏 ⚠️

- **载体形状 ✅**：NOD = 图事件（每节点 = 配方：op + dest/srcs + 类型码 + 边）——格层本体条款 1「值 = 配方」的载体承诺正确
- **op 语义 ⚠️**：NOD 的 op/dest/srcs 语义 = **v5 instrs 相同**（v6 spec 设计原则 6 明言：变量槽模型保留，为 corearch 最小改动）——这是**显式妥协，不是哲学决定**：
  - ① 存储形状泄漏：变量 = vars 表 id = 槽；LOAD/STORE/LOAD_FIELD/LOAD_INDEX… 的语义 = 字节内存操作（G1-3：位置 = 字节地址形态）
  - ② 控制形状泄漏：JUMP/BRANCH/LABEL/RETURN/CALL = 行式控制流形状（G2-1 边线）；REG 提供嵌套但 op 语义仍按「执行路径」组织
  - ③ 编码选择泄漏：tag/2L 相关 op 与帧 tag 语义在 op/类型码面（G3-1：换平台编码选择被当作 op 语义）
- **正面先例 ✅**：ENT 版本化规则对 STORE 的勘定（定值目标在 s1，ρ(s1):=ρ(s2)——v6 spec §3.4）——**赋值 = 版本化（条款 5）的正确语义雏形**，审计底稿中作为「格语义形状」参照系
- **op 全集裁决方法**：逐 op 以 Task 0 盘点清单 3（ast.cr 编号 0-51 全分类）为底稿，按 G1-G4 裁决——**裁决结果 = §4.1 的输入表**（本 spec 不逐 op 落表；新工作引用本 spec 时按 §1 判据 + 清单 3 底稿执行，落表 = 引用者的任务）

### 2.3 ENT（条目表 = 存在结构核心）——格本体正确形状，两处问题 ✅⚠️

- **形状 ✅**：条目 = (var_id, version, def_nod, 存在区间, home, flags)——「条目 × 版本 = 赋值条款 5 的直接载体」、「位置 = (条目标识, 偏移) 条款 6 的位置形态」、「身份 = def_nod（图节点）」——**ENT 是格层本体在 v6 里最纯的成分**
- **问题 1 ⚠️ 恒空未主干化**：regalloc 移后端（2026-09-07）后 ENT 恒空（loader 空表语义支持、零 version bump）——存在结构 = 侧表，实际主干仍是 NOD 线性流
- **问题 2 ⚠️ home 字段的语义定位**：home = 分配器回填槽位。裁决：**home = 缓存语义映射实例的注记**（同族于「寄存器分配 = 缓存语义映射实例」；regalloc 移 corearch 后 -1 直通 = 已在实例化走向）——格本体最小集 = var_id/version/def_nod/区间/flags，home 可留但语义定位 = 实例层数据

### 2.4 REG（region 表）——格侧成立 ✅

SG 嵌套 + 区内条目范围 = 图锚定区域/共存推导的坐标载体（G2-4：共存不落盘、sweep 推导 = 最弱理论形态）——**格侧成立**。区域 = 经典映射实例的组织面（memory-model §二），但 region 结构本身（嵌套坐标） = 图语义 → 保留在格侧正确。

### 2.5 NOD 边表缺席（v6 开放点 1）——格层纯度缺口 ⚠️

- 现状：边表 v6.0 可省略（文件序 = 合法拓扑序 → 重建无成本）
- 裁决：**边 = 配方语义的必要成分**（条款 1「(产生它的图节点, 输入边)」——缺边则配方不完整，「图 = 真相层」的文件载体不闭合，文件序退化为「另一种程序」的执行序——G2-1 从「序列化」滑向「程序顺序」）
- 落盘与否 = 编码层事务（v6 spec §7 开放点 1 的编码层定性正确）；语义存在性 = 格层必需——**格形态的纯度判据：文件必须能重建图语义（含边），执行序只是图的一个投影**

### 2.6 实现现状注记（本 spec 裁决为格式设计层；代码现状以复核为准）

- v6 spec 头部声明「代码按实施计划推进」；regalloc 移后端记录：ENT 恒空、opt_meta 恒 0、first_ent/param_ents 恒 -1、loader 空表语义已支持
- NOD op 与 v5 instrs 的精确对应、边表是否实际落盘、tag 元数据是否在 .ccr 内——**引用本 spec 做具体裁决前，以 ccr_io.cr / corec lower 阶段复核为准**

### 2.7 产出：不纯点清单与洗纯边界

不纯点（按 §1 判据点名）：

| # | 位置 | 泄漏类 | 程度 |
|---|---|---|---|
| P1 | NOD op 语义 = v5 变量槽指令 | ①+②+③ | 结构性（v6 设计原则 6 的显式妥协） |
| P2 | ENT 恒空未主干化 | （本体缺位而非泄漏） | 结构性 |
| P3 | NOD 边表缺席 | （配方不完整） | 结构性缺口 |
| P4 | ENT home 混入格本体语义 | 实例注记定位不清 | 轻（语义定位裁决即可） |

**洗纯边界声明**：本 spec 只定判据与目标纯度，**不设计 v7、不改代码**。P1-P3 的修复方向（NOD 配方语义化、ENT 主干化、边表语义必须）指向未来的格式演进——凡涉格式重构的工作须先过本 spec 判据；「洗纯边界内可修」（P4 类语义定位 + 不触格式的判据应用）可随时按本 spec 执行。

## 3. corearch 转换器契约

### 3.1 定位

corearch = **格 → 编码投影器**：把格语义对象（条目/版本/配方/区域）投影为具体机器的物理编码。**不是执行器**——执行标注空间（FIXPT/模糊/神谕/BSS/CORE）属于图（dataflow-design §8）；「图执行契约」定义为图层事务（HIT spec §7 YAGNI 现状维持——本 spec 不推翻，仅确认：格→编码投影不需要理解范式）。编码层绑定经典机 = 合法且必须（z-vision 三层链），**问题只在绑定形态**（§3.3 C3）。

### 3.2 C1 —— 输入契约（纯格）

- 转换器输入 = 纯格形态：条目 × 版本（ENT 语义主干）+ 图事件/配方（含边，语义完整可重建）+ 区域嵌套（REG）+ 符号/类型信息
- 现状 .ccr 的泄漏（§2.7 P1/P3）在转换器**入口做归一化**：把变量槽/字节操作形状还原为条目/版本/配方语义后再投影——**泄漏不得作为转换器的输入假设向下传播**（现状转换器把槽 = rbp 帧偏移当输入假设 = 病灶的机制形态）
- 归一化层自身的正确性判据 = 语义保真（还原后格语义 ⊇ 原形状可观测语义——引用缓存语义条款 7 的映射实例正确性方向）

### 3.3 C2 —— 输出契约（实例形态）

- 输出 = 目标机物理编码（今日 x86 ELF）。经典绑定在**实例层**全部合法：
  - **实例数据**：投影表/模板（HIT 表 = 正确载体方向，§3.5 C4）
  - **实例算法**：帧布局（prologue/epilogue/帧公式）、调用序列（参数拷贝/返回协议）、寄存器缓存映射（regalloc = 已接纳先例）、tag/2L 编码选择——**全部为映射参数实例**
- **实例算法推广先例**：`regalloc-cache-mapping`（寄存器分配 = 缓存语义映射实例）是已接纳的实例化样板——帧布局/ABI/调用序列/tag 编码与寄存器分配同族（对缓存语义的机器侧资源决策，G3-2），**同族必同类处理**：入实例层，不入通用机制

### 3.4 C3 —— 转换器核心只含通用机制

核心允许（且只允许）：

1. **格语义 → 实例请求的通用翻译**：版本 → 位置分配请求、共存 → 资源互斥约束（判定四条形态）、配方 → 指令选择请求、区域 → 存储区段请求
2. **实例注册/选择机制**：目标机实例（数据 + 算法）的登记、校验、按需装载

核心禁止（= G3 判据的可执行形态）：帧公式、寄存器名、ABI 参数序、tag 位布局、调用序列、ELF/rodata 布局等**硬编码进通用机制**。凡现 corearch 硬编码处 = 泄漏点，去向 = 实例层。

### 3.5 C4 —— M2/HIT 裁决

1. **方向 ✅**：HIT 表驱动 = 编码层实例数据的正确载体（「换表即换平台」 = C2 实例数据形态的兑现路线）——不废弃
2. **定位偏差 ① —— 判据错**：M1/M2 的对照判据 = 表路径 ELF **逐字节等于旧发射器产物**——服务对象错了：模板的正确性判据应为「格语义 → 实例的投影正确性」（行为/结构等价 + 映射正确性定理方向，缓存语义条款 7），不是复刻注定退役的旧发射器的字节（含其偶然形态：冗余 REX 位、jmp rel 0、ret_patch 戏法）
3. **定位偏差 ② —— 范围窄**：M2c 数据化只覆盖单指令编码形态（清单 1），帧/ABI/调用/返回序列（清单 2 R1/R2/R7 等）仍留代码——**实例化边界应覆盖全部实例算法族**（R1-R12 按 G3-2 裁决：实例算法 → 参数化进实例层；纯翻译机制 → 留核心）
4. **具体症状消解**：ret 裸 C3 矛盾、branch 模板四原子 vs 两步文本矛盾 = 旧字节复刻判据的必然产物——按本裁决重定判据后，模板 = 实例的正确语义序列，不再追旧字节

### 3.6 C5 —— 挂账裁决

- **「事件流/表数据入 v6 段（NOD op ↔ HIT event_id 对齐）」（TODO 挂账）**：裁决 = **事件流与表数据 = 编码层事务**（x86 实例的投影内容），不入格形态段——格形态携带语义对象，不携带任何目标机的投影中间物；NOD op ↔ event_id 对齐 = 编码层实例注册问题（实例数据引用格语义对象的方式），非格内容
- **regalloc 移后端（已完成）** = C3/C2 的正面先例（分配判定 = corearch 内实例化 + .ccr 不承载分配结果 = 实例数据不出现在格格式）——方向确认

## 4. 应用指引

### 4.1 裁决流程（引用本 spec 的新工作）

1. 对象过 G1-G3 判据 → 泄漏则 G4 点名

### 4.2 即时应置（M2 停摆注记）

- HIT M2a Task 3+（branch/call/ret 模板实施）**挂起**——原因 = C4 判据裁决前不扩大旧判据下的实施；复启条件 = 按 C4 重定对照判据（或用户另行拍板）
