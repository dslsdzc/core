> 一句话：**int 在语义层 = 数学整数的公理化接口（无溢出概念）；「64 位」「i64 上限」「环绕」全部是编码层（hw-map 域）的经典投影实例形状——溢出不是语义事件，溢出错也不是语义错误。**

## 一、语义层定稿：int = 数学整数公理化接口

1. **int 是数学整数（Z）的公理化接口**，不是任何位宽机器整数。语义承诺：
   - 加法/乘法满足结合律、交换律、分配律；序为全序；无最大/最小值（无界双向）；
   - **无溢出概念**——`x + y > x`、`x * 2 / 2 == x` 之类性质在语义层无条件成立，与在规约层（CIC 整数 Z）证明的结论一致（spec-design §9.4：翻译桥在 int 上无分歧）；
   - 溢出**不是语义事件**：没有「值越出 int 域」的状态、错误或行为——int 域无边界，值只会超出某个**投影**的承载形状。
2. **接口地位**（type-system-direction 定案 #2）：int = 原生接口条目——规则内建在编译器、公理引用规约层、用户不可实现（公理是编译器领地，防伪造证明）。语义保鲜：图节点标注 + 规则解释，int 的性质是图上的契约不是代码约定。
3. **纯数学叙事**（type-system-direction §二）：int 无上限、dex 精确 = 公理化接口 + 原生实现——原语语义也可对照验证。本文档是 int 这条目的语义定稿。

## 二、编码分层（hw-map 域）：经典 64 位 = 快路径投影

1. **语义层无宽度**：宽度（i64/u32/w32…）不进入语言类型/标签体系（width-out-of-language——单标签单范式；apx 保持单一语义 = 精度降级开关，不扩张为宽度标签）。
2. **经典 64 位机器字 = 快路径投影实例**：今天全部实现（自持编译器内部表示、ELF 后端、解释器）都是「把数学整数投影到经典 64 位机器字」的一份实例；同语义可有其他投影（任意精度载体、多字、扩展表示、未来范式）。
3. **超界值 = 编码层事务**（方向性承诺，落在图推导 pass 家族，见 §六挂账）：
   - **静态区间证明免检**：图上的区间传播/符号证明（与 TODO `bounds-inference` 图推导边界 pass 同族——下标/长度证明的推广形态）证出「此值恒在该投影形状内」→ 不发射检查/不升级，**证明成功零成本**；
   - **证明不了才检查/提升**：区间证不出 → 运行时检查（保形状内）或提升表示（换更大形状）——检查/提升是编码层兜底，不是语义事件；
   - 表示策略（扩展/多字/BigInt、何时提升、提升形态）= **hw-map/远期事项，非本语义层承诺**。
4. **三层映射对应**：图/格 = 纯数学（int 语义在图/格层无界，值不携带宽度）；编码 = hw-map 领域（64 位形状、环绕、格式字段宽都是编码层实例参数）。
5. **与数值类型设计（2026-08-16/08-23）的措辞关系**：该设计说 int 实现 = 「i64 快路径，装不下时自动升级为堆上 BigInt，无溢出错误」——其语义意图（永不报「溢出错误」、数学语义）本定稿继承；其**表示策略措辞**（具体升级时机/形态）按 width-out-of-language 归编码层/hw-map 域，非语义层承诺。语义（无上限）是已决项，表示（怎么装得下）是工程项——两者分属两层，不在本文档混淆。

## 三、错误分类定稿：溢出类错误 = 编码层限制错误

**分类原则**：错误发生在哪一层，就归哪一层。「整数太大」不是语义错误——语义层 int 无上限、无溢出概念；它是**投影到经典 64 位目标时的形状限制**（该值在当前经典投影中无载体）。现有溢出相关错误路径逐一归位：

| 错误路径 | 位置 | 归类 |
|---|---|---|
| lexer 字面量守卫「integer literal overflow」（十进制 > i64max 及各进制的 base 校准阈值） | `src/compiler/lexer.cr` `str_int_literal` / `bootstrap/corec/frontend/lexer.py`（前缀进制守卫） | **编码层限制错误**——编译器内部表示 = 经典 64 位机器字（快路径投影），字面量超形状 = 投影限制拒绝；非语义错误（语义层可表示任意整数） |
| dex 字面量整数部分过宽「decimal literal integer part is too wide」 | `src/compiler/lexer.cr` `str_to_scaled`（定点 S=10⁶，整数部分 ≤ 9.2e12） | dex 表示层现状限制（定点方案形状；见 TODO `dex-precision`）——同族但属 dex 线，不并入 int 线 |
| CCR i32 字段校验拒写（`ccr_i32_fits` / `ccr_validate_i32_fields`：IR 指令索引、region 字段超 i32 不落盘） | `src/compiler/ccr_io.cr` `save_ccr` | **编码层文件格式限制**——v6 段表格式字段宽 i32（文件布局形状），本就归编码层（hw-map 域 = 经典投影实例）；与 int 语义无涉，仅在此归位 |
| 死错误码条目 `EC_P_LIT_OVERFLOW`（P019）、`EC_R_OVERFLOW`（R003） | `src/compiler/ast.cr`（定义无发射点） | 挂账注记——若将来启用 R003，其语义必须是「经典投影运行时机器字环绕事件」，**不是语义溢出**（语义层无此事件）；勿在启用时把语义层写成可溢出 |

**调整方式与保守边界**：以上是分类（语义层无此概念 → 编码层限制），不是行为变更——字面量拒绝、CCR 拒写照旧（当前编码只有经典 64 位一份投影，拒绝是形状事实）。错误文本/诊断码体系不动（见 §七注记）。

## 四、与 dex 精确/任意精度：两线不混

1. **int 无上限 = 语义层事实**（公理化接口，表示延后，§一/§二）；**dex 精确 = 表示层工程**（精确小数需要表示层实现才成立）。两条线不混：
   - int 的「无上限」在图/格层已封闭——语义不依赖任何表示工程；「装不下」永远只是投影问题（§二 3）；
   - dex 的「精确」依赖表示层现状：定点 S=10⁶（`src/stdlib/dex.cr`）——6 位小数 + int64 硬上限（加减 ≤ 9.2e12、乘 |a|·|b| ≤ 9.2e6），设计意图与实现为语义级偏差（已记账 TODO `dex-precision`：修复方向 = 动态位数任意精度，重活排期）。
2. **不混的含义**：int 的无上限**不是**「表示层做任意精度工程」的承诺——int 语义不欠表示债（债在编码层投影与 hw-map 策略）；dex 的精确是表示层债（表示达不到则语义达不到）。int 不因 dex 挂账而等待；dex 不因 int 无上限而自动精确。
3. **apx** 保持单一语义 = 精度降级开关（机器语义授权，CPU 后端兑现 binary64），只作用于 dex 类表示层选择，**不成为 int 的宽度标签**（width-out-of-language 明示）。

## 五、与验证衔接：int 公理可被规约对照验证（CompCert 精神）

1. **规约直映**：int 公理可被 .cr requires/ensures（.corespec 规约层语法）表达——`requires x >= 0`、`ensures result * result >= 0` 等数学整数性质直接成立；int → CIC Z 翻译桥无分歧（spec-design §9.4），规约证明与图语义同一整数域，**不需要位向量/溢出模式建模**。
2. **原语语义对照验证**：int 公理化接口 = 原语层的「语义模型」——编译器（及投影）的正确性可与公理接口对照验证，CompCert 精神从「后端对 C 语义」推广到「原语对数学语义」（type-system-direction §二 纯数学叙事）。这是后续验证切片的证明义务来源：不是证明「int64 不溢出」（经典投影下可证伪），而是证明「编码层投影/拒绝行为与无界语义一致」（形状内 = 值相符；形状外 = 拒绝或显式提升，永不静默错值）。
3. **免检先例同族**：静态区间证明免检（§二 3）= spec-design 已有「编译期证明免检的规约版」先例（DEREF 运行时边界检查在证明后直接消除）与 checker R002 编译期越界拒绝的推广形态——三态（证明恒安全 → 免检零成本 / 证明恒越界 → 编译期拒绝 / 证明不了 → 保留运行时检查并带图推导必要性标注）与 TODO `bounds-inference` 同构。

## 六、现状盘点与挂账

- **现状（均为经典 64 位投影实例行为，语义定稿后不变）**：
  - int 运算：int64 机器字环绕、无陷阱（dex.cr 注「越界环绕——无陷阱，与 int 溢出一致」为同一投影事实）；
  - 字面量入口：超 i64 形状 = lexer 拒绝（§三）；
  - .ccr 落盘：超 i32 格式字段 = 拒写（§三）；
  - 解释器/Python bootstrap 内部：Python int 任意精度——同一语义的另一份投影实例（两编译器「分歧」在此叙事下不是语义分歧，是各自投影形状不同；`1_000` 分歧复核仍按 width-out-of-language 语言侧清理推进）。
- **挂账**（本语义定稿派生，均非语义层承诺）：
  1. 图推导区间证明 pass（bounds-inference 同族推广：值区间传播 → 免检/拒绝/保留检查三态，§二 3）；
  2. hw-map 表示策略（扩展/多字/提升形态——远期）——**M1 实例已落地（2026-09-07）**：add/sub 溢出 2-limb（128 位固定）多字投影完成（64 快路径 + jo 检测 + tagged 槽），见 `specs/2026-09-06-int-multiword-backend-design.md`（§8 M2 挂账：mul/div、打印、超 64 常量、动态增长、静态免 tag 等仍挂）；
  3. lexer 溢出守卫消息文本与诊断码体系（§七注记）；
  4. R003/P019 死错误码条目启用时的语义边界（§三末行）。

## 七、注记：错误文本维持方案（任务 B 落实结论）

**现状评估**：lexer 溢出消息无诊断码（`print_parse_errors` 直打 `error: <msg>`，diag.cr）；CCR 拒写路径返回 -1 无消息；两处均无测试断言消息文本（唯一断言的「too wide」属 dex 线消息，不动）。

**决策：注释归位 + 文档归位，错误文本与错误码体系不动**，理由：
1. 分类调整的消费方是「人读的语义框架」——文档 + 守卫注释已完整承载；行为无需变（当前只有经典 64 位一份投影，拒绝是形状事实）；
2. 自持编译器消息改动需全量重建（`build_selfhost_native.py`，铁律 CPU ≤ 10% 下耗时甚巨）且并行会话共享工作副本/build 目录，重建互相污染；价值 ≈ 0（消息仅超界字面量用户可见）；
3. 文本若要与「编码层」语义对齐，应随 lexer 诊断错误码体系建立一并做（P019 死条目在 ast.cr 等待归位），避免同一文本两轮演化。
**未来若动**：消息宜改为「超出经典 64 位编码宽度」类表述（语言无上限、经典投影受限），或在诊断前缀区分层类别；错误码启用时 R003 语义按 §三末行边界。
