## §0 范围与裁决

### 0.1 论题

把「不可信数据 → 解释器语法位」变成**非法边**：

> **值位（value position）合法；语法位（syntax position）非法；参数化通道（结构由库的类型化构造器给出、数据走值位）合法。**

判据的第一性来源是**构造器封闭**（库声明的形状项只有库自己的构造器能产生），**不是污点传播**——这是本族不退化成 lint、也不退化成全局污点分析的原因（§1.3）。污点（属性轴）只在「未包装 API 的裸位置」这一退路里承担判据（§2.4），且作为 S-A 轴基础设施的消费者出现，不是本族自建的第二套体系。

### 0.3 术语用法声明

本文使用路线图 §1.1 的术语：**属性轴** / **义务** / **四档义务**（prove · enforce · proof-required · reject）/ **policy** / **declassify** / **sink / source 模型**——**不重定义**。本族新引入的局部词汇（仅本文使用，不外溢）：

- **位置（position）π**：一次调用实参槽（含方法 `self` 槽）、或等价的「值进入解释器的入口」。位置种类 `kind(π) ∈ {value, syntax(D,φ), syntax_raw(D)}`。
- **领域 D**：下游解释器标识（`sql` / `html` / `sh` / `fmt` …）——**开放的字符串标识，不是语言枚举**（新领域不改编译器）。
- **位置形状项 φ**：该位置允许的值的类型项（R2 §1.2 τ），由库给出。
- **裸位置（raw position）**：库无法用类型表达、只能由策略数据声明为语法位的位置（典型：C 库/未包装 API，`system(char*)`）。

## §1 非法边判据

### §1.1 位置种类的操作性定义（为什么它必须由库声明）

> **语法位判据**：位置 π 是领域 D 的**语法位**，当且仅当**下游解释器 D 对 π 处的字节做分隔符/结构再扫描（re-scan）**——即这些字节中若出现 D 的元字符（或分隔约定），会改变 D 对结构的判定。否则 π 是**值位**。

判定测试（对分类的交叉检验，也是库自我审查的检查表）：

| 位置 | 再扫描？ | 种类 |
|---|---|---|
| `execve` 的 argv 元素 | 否（内核按 NUL 边界取整段，不再扫描内容） | 值位 |
| `sh -c <line>` 的 line | 是（`;` `\|` `$()` 空白分词） | 语法位（`sh`） |
| SQL 绑定参数（prepared bind） | 否（协议按长度传值给引擎的**值**槽） | 值位 |
| SQL 查询文本 | 是（`;` `'` `--`） | 语法位（`sql`） |
| HTML 元素体文本节点 | 否（解析器到此已是文本节点） | 值位 |
| HTML 属性值 / URL / 内联 JS | 视上下文（引号/`&`/`:`/JS 元字符） | 语法位（`html` 的对应子形态） |
| HTTP 头的**值**字段 | **是**（CRLF 是分隔符） | 语法位（`http`） |
| 长度前缀协议的载荷 | 否 | 值位 |

该定义**只能由库声明**、不能由编译器推断：它是对**下游解释器**（DB 引擎、浏览器、shell、内核接口）性质的陈述，编译器看不到下游。这正是路线图原则 2「策略面归库」在本族的落点——**语言不内建任何领域的元字符表**（原则 2 的禁令：任何「SQL 字符串字面量检查」式特判都是 lint 换皮）。

### §1.2 形式化：源属性 × 目标位的合法性关系

记号（全部复用既有机制，无新判定体系）：

- `τ(v)`：值 v 的**类型项**（R2 §3.1 `g_type_terms`；图上标注，迁移期双槽）。
- `trust(v)`：v 的**可信度**标注（S-A 的属性轴之一；**推导产生，用户不写**）。
- `φ`：位置 π 声明的**形状类型项**（R2 §2.2 横切轴 / §2.3 用户轴条目）。
- 位置约束项 `κ`：附着于 φ 的**档位约束**（常量档 / 符号档 / 动态档，F11 三档，R2 §5.1 长度约束项的先例形式）。

**合法性判据**：

```
Legal(v, π) ⟺
    kind(π) = value                 → ⊤                        （值位，无义务）
  ∨ kind(π) = syntax(D, φ)          → ty_sub(τ(v), φ) = 真       （类型判据 · 主）
                                        ∧ 档位约束 κ 满足        （常量档等附加约束）
  ∨ kind(π) = syntax_raw(D)         → ⊢ Trusted(v)             （属性判据 · 仅裸位置）
```

- **非法边** = `¬Legal(v, π)`。在图上表现为：**不存在可建的合法 semantic edge**——拒绝是**图不完备**（无合法边），不是「边上加运行期守卫」（§0 裁决 6）。这与路线图的「非法边」措辞严格一致，且更弱：不需要先说「边存在再检测到非法」。
- 判定走引擎（原则 4）：`ty_sub` / `iface_satisfies`（形状满足，R2 §2.5）/ `ty_witness`（失败给**具体反例值** → 诊断「值 X（来自 `io.read_file`，`test.cr:12`）不是 `SQL<Structure>`」）。
- **与 S-A §3.3 的接法（已定）**：上式三种 `kind` 统一写成 S-A 的单式

  ```
  判定 = ty_sub( τ(v) ⊓ A_trust(v) , Shape(π) )        ⊓ = 引擎 INTER
  ```

  ——`Shape(π)` 由 policy 数据给出：值位 = `⊤`（恒真）；`syntax(D,φ)` = `φ`（+档位约束 κ）；`syntax_raw(D)` = 该策略的 `Trusted` 形状项。**不新增判定算子、不新增规范化规则**（S-A §3.3 同一要求）。
- **陷阱注记（本族对 S-A §3.3 的补充，实施批必读）**：单式里的 `⊓` 与 `⊥` 有一个会**架空判据**的退化路径——若 `A_trust(v)` 以**否定形式**展开（如不可信 ↦ `¬Trusted`），而左侧值项本身已含该标注（如库构造出的 `SQL` 值被标 `untrusted`），则左式 = `SQL ⊓ ¬Trusted = ⊥`，而 `⊥ ⊑ 任意 φ` **恒真** ⇒ 判定放行一个不可信值 ⇒ **静默通过**（违反原则 3）。**规范约定**：`A_trust` 只做**加约束式单调展开**（可信 ↦ `Trusted`，不可信 ↦ `⊤`＝不加约束），属性要求一律写在**右侧** `Shape(π)`；实施批须配负控（N5，§6.1）锁死该约定。
- **未判定不静默**（原则 3 + R2 §3.3 预算守卫）：`ty_sub` 返回 unknown（预算耗尽 / 未覆盖面）时，**不得当通过**，按 S-A §2.2 决策树落 ③/④ 并登记（§5）。

**为什么不需要流敏感分析**：判据只读 `τ(v)` 与 `trust(v)` 两处标注，与 v 的**定义路径、别名、中转（laundering）无关**。把不可信字符串存进结构体字段、经函数返回、经容器搬运，都不会改变它到不了语法位这一事实——因为**唯一的入口是库的构造器**。这是形状项判据相对污点分析的结构性优势，也是 §3「if-校验旁路」不成立的根因。

### §1.3 构造器封闭 = 非法边的第一性来源

`φ` 是**库声明的**形状类型项，其 inhabited 值只能由**声明返回 φ 的构造器**产生：

- **类型层封闭（自动获得）**：任何 `fn f(...) -> φ` 的函数体若返回非 φ 的值，被普通返回类型检查拒绝；因此「凭空造一个 `SQL<Structure>`」在类型层做不到。
- **数值层封闭（须策略给出）**：`φ` 的某个构造器若同时接受「不可信来源可满足的类型」（如 `string`），则它是**开口**——策略必须二选一：① 给它附**档位约束**（解析式位置 = 常量档，动态实参不满足，§2.2），或 ② 把它登记为净化节点（§3，带后置条件义务）。
- **封闭性的现实缺口（登记）**：Core 今天**不强制** `pub`（`parser.cr:697` 只写 `is_pub`，全仓无消费）⇒ 库外代码若被允许构造 `φ`，封闭性只能靠「类型层封闭 + 库实现为 TCB」维持。见 §8-开放问题 1。

一句话：**「不可信数据不能到达语法位」之所以是非法边，不是因为我们追踪了它，而是因为语法位的类型里没有一条从 `string` 出发的边**——唯一存在的边（构造器）由库把守，库的边要么带常量档，要么是一处显式、可审计的净化节点。

### §1.4 与 `string` 的关系（零标注）

`string` **不变**：仍是原生八员之一（R2 §1.2），不拆成 `Trusted<string>` / `Untrusted<string>`，既有签名零改动。不可信性不是类型，而是：

1. 一处**推导得到的标注** `trust(v)`（S-A 轴；仅在裸位置判据里被读）；
2. 一条**形状项判据**——`string ⊄ SQL<Structure>`（`ty_sub` 直接给「否」）。

因此 §4 的渐进引入不需要动任何既有代码。

## §2 领域库接口约定

**声明总原则**：库只声明三件事——**① 未包装的语法位（若有）② 不可信来源函数集 ③ 净化节点及其后置条件**。**构造器不需要在策略里声明**：构造器由**类型**给出（返回 `φ` 的函数即构造器），这是「策略面最小」的关键（data, not syntax；路线图 §1.1 `policy` 定义）。

**与 S-A §3.1 的关系**：本族的这些声明就是 S-A policy 条目里 `<source 声明集>` / `<sink 声明集>` / `<declassify 通道>` 三栏的**填法**——S-A 定栏目，本族定填法（含「sink 的语法位/值位之分」这一 S-A §3.1 已点名的 S-B1 专属字段）。条目的注册走 S-A §3.5 的插件标签通道（`register_plugin_tag`），**语言零语法改动**。

示意的声明记法（**语义示意**，非语法提案；语法落地归 R2 §2.3 的 interface 重定义与实施批）：
`shape` = 形状类型项声明；`ctor` = 返回该形状项的构造器；`src` = 不可信来源；`pos` = 位置声明。

### §2.1 共同结构

```
shape  D<Ph>            # Ph = 阶段/上下文参数（本族的设计形态；参数化判定能力见 §6 依赖）
ctor   ... -> D<Ph>     # 构造器（库函数，返回形状项即成立）
src    fn_name          # 返回不可信值的函数（来源）
pos    fn:slot ...      # 语法位声明（仅未包装 API；已包装者由参数类型承担）
decl   fn -> Trusted [+ post]   # 净化/declassify 节点（§3）
```

### §2.2 例一：SQL

- **下游**：DB 引擎的 SQL 解析器；元字符 `;` `'` `--` `/*` 改变结构。
- **形状项**：`SQL<Ph>`，`Ph ∈ {Text, Structure, Frag, Param}`。
- **解析式表示（文本形态）**：`sql_text(lit: string) -> SQL<Text>`，其中 `lit` 带**常量档约束项 κ=const**——即查询文本必须是编译期已知的常量（源码字面量）。动态字符串**不满足** κ ⇒ 拒绝（不是运行时验证）。对应「查询文本 = 代码，不是数据」的直觉，且复用 R2 §5.1 F11 常量档机制。
- **拼接式表示（结构形态）**：

```
sql_select(cols: [SQLFrag], from: TableRef, where: Cond) -> SQL<Structure>
sqlfrag(x: SQL<Frag>)              : SQL<Frag> + SQL<Frag> -> SQL<Frag>
sql_param[T](v: T) -> SQL<Param>                 # 值位通道：不可信值从这里进
SQL<Frag|Structure> + SQL<Param> -> SQL<Structure>
SQL<Structure> + SQL<Structure>  -> SQL<Structure>   # 仅结构 + 结构
```

- **sink**：`sql_exec(q: SQL<Structure>, binds: [SQL<Param>])`。`q` 是语法位，其**声明类型即形状项** ⇒ 判据自动成立；`binds` 是值位（prepared bind，引擎按值消费）⇒ 不可信数据合法搭载。
- **危险逃生口**：`db_raw_exec(text: string)` 这类「整串文本执行」API **不由库提供**。若某库坚持提供，则策略**必须**把该槽声明为 `pos syntax_raw(sql)`，判据退到属性面（§2.4）。
- **来源**：`io.read_file` / `cli.argv` / `net.recv` / `os.get_env`。
- **正/负控**：`sql_exec(sql_text("SELECT ..."), [sql_param(u)])` 合法（`u` 不可信亦可）；`db_raw_exec(read_file("q.sql"))` 非法边。

### §2.3 例二：HTML

- **下游**：HTML 解析器；`<` `>` `&` 引号；且**上下文敏感**（元素体 / 属性值 / URL / 内联 JS 规则各不相同）。
- **形状项**：`HTML<Ctx>`，`Ctx ∈ {Text, AttrValue, URL, Elem}`（JS 上下文单列为高危子形态，默认不进白名单）。
- **值位 = 文本节点 / 属性值**（这就是「参数化通道」的形态）：

```
html_text(s: string)        -> HTML<Text>        # 转义 = 位置化（§3.1）
html_attr_value(s: string)  -> HTML<AttrValue>
html_elem(tag: Tag, attrs: [Attr], children: [HTML<Text>]) -> HTML<Elem>   # Tag = 闭枚举白名单
html_parse(lit: string /*κ=const*/) -> HTML<Elem>                          # 解析式：模板须为字面量
```

- **负控**：`html_elem(div, [], [read_file("u.txt")])` ⇒ `children` 槽要求 `HTML<Text>`，实参 `string` ⇒ **非法边**。而 `html_text(read_file("u.txt"))` 合法——注入的非法性完全由「不存在 `string → HTML<Ctx>` 的边」表达，**唯一的边就是被声明为净化的构造器**（`html_text` 是 `string → HTML<Text>` 的唯一映射）。
- **形态细分粒度不足的残留**：`HTML<AttrValue>` 对 URL 上下文不安全（`javascript:` 是合法的属性值文本），需要库把 `href` 另立 `HTML<URL>` 并给出 URL 校验构造器——**粒度不足 = 库的规格错误**（§7-①）。

### §2.4 例三：shell（同时展示两条通道）

- **下游**：`/bin/sh -c <line>` 的整行；元字符 `;` `|` `&` `$()` `` ` `` 空白分词。
- **通道 A —— argv 形态（值位，安全）**：

```
sh_run(prog: Sh<Prog>, args: [Sh<Arg>])     # 对应 execve(2)：内核不再扫描参数内容
sh_arg(s: string) -> Sh<Arg>                # 值位通道，不可信值合法搭载
```

  负控：`sh_run(sh_prog("ls"), [sh_arg(read_file("p.txt"))])` **合法**——这是设计意图，不是漏洞（内核不解析参数）。
  **诚实边界**：argv 值位只保证**不改变结构**，不保证**语义安全**——`sh_run(sh_prog("rm"), [sh_arg(untrusted)])` 的选项注入（`-rf /`）在本族判据**之外**（§7-附加）。
- **通道 B —— 文本形态（语法位）**：

```
sh_text(lit: string /*κ=const*/) -> Sh<Text>      # 解析式：整行命令须为源码字面量
sh_quote(s: string) -> Sh<Quoted>                 # 净化节点：单引号包裹 + ' 转义
sh_run_text(c: Sh<Text|Quoted>)                   # 接受常量文本或已引用片段；不接受 string
Sh<Text> + Sh<Quoted> -> Sh<Structure>            # 组合仍只接引用片段
```

  `Sh<Quoted>` 与 `Sh<Text>` 的**区分**是防止「把未引用片段拼进来」的机制——形态参数在这里承担了「片段合法性」的判据。
- **裸位置（本族唯一必须退到属性判据的地方）**：libc `system(cmd)` / `popen(cmd)`（参数是 `string`，库无法重新定型）。策略：

```
pos syntax_raw(sh) system:0
pos syntax_raw(sh) popen:0
```

  判据退到 `⊢ Trusted(v)`：`system("ls -l")`（常量 ⇒ `Trusted` 可证）**通过**；`system(read_file("x.sh"))` **拒绝**。这是属性轴在本族的唯一落点，也是「未包装 API 规模问题」的入口（§8-开放问题 8）。
  **现状事实**：本仓库已存在该 sink 的真实实例——`src/stdlib/os.cr` 的 `system(cmd: string) -> int`（`fork()` + `execve("/bin/sh", ["/bin/sh","-c",cmd])`），这正是 S-A §6.1 选定的首切片对象；本族切片 1 与它**互补不重叠**（§6.1）。

### §2.5 同一判据的第 N 个领域（非特判证据）

`fmt`（格式串）、`ld`（路径段，与 S-B4 边界重叠，§4.8）、`http`（头值字段，CRLF 再扫描）、`json`（键名/字符串值）、`regex`（模式文本）、`ld.so`（`LD_PRELOAD`）——**同一个判据，只是 D 与 φ 不同**。编译器侧代码路径**零增长**：新增领域 = 库新增一份策略数据 + 形状项声明。这是「不做成特判」的可检验表述（§6 判据 D4）。

## §3 净化（sanitize）与 declassify 的语义

### §3.1 净化 = 位置化，不是「清洗」

库的净化构造器**不做**「从字符串里删掉危险子串」的语义，而是做**位置化**：把不可信值放进下游解释器**当数据消费**的位置，并把这个事实写进**返回类型项**。

- `html_text(u) -> HTML<Text>`：不是「u 被清洗了」，而是「u 被放进了元素体文本节点这个值位」；
- `sh_quote(u) -> Sh<Quoted>`：不是「u 里的 `;` 被删了」，而是「u 被放进单引号片段，shell 分词器到此不再切分」；
- `sql_param(u) -> SQL<Param>`：不是「u 被转义」，而是「u 走 bind 协议进引擎的值槽」。

这个重述有实质后果：**净化的正确性条件 = 位置声明的正确性**（§1.1 的再扫描判据），而不是「正则写得对不对」。HTML 的例子说明它并未消除全部风险：位置声明的**粒度**决定精度（属性值 vs URL vs JS）。

### §3.2 declassify 节点：显式、可审计、产生义务

`declassify` 是共享契约定义的唯一合法通道（`Secret → Public` 同构地 `Untrusted → Trusted`）。本族取定三条约束：

1. **必须显式成节点**：只存在两类合法通道——(a) 类型变化的位置化构造器（§3.1）；(b) 同型放行的 `declassify`（如 `sql_ident_checked(s: string) -> Trusted`，库声明后置条件 `is_ident(s)`）。二者都在图上是一个**节点**，不是一处标注、不是一个 pragma。
2. **可审计**：节点进 S-A §5.2 的**三面可见**（诊断面 / 义务台账面 / 产物面）+ `core explain` 决策通道（S-D）；「这个程序的不可信数据从哪进、经哪放行、到哪止步」可被一条命令答出。净化节点在台账中的记录字段 = S-A §5.2b 的义务项（轴 / 源 / 汇 / 落档 / 状态 / 图→源码映射）。
3. **产生义务而不是免单**：`declassify` 声明的是**库的后置条件**，义务是「证明该后置条件成立」——落 proof-required（VC 由验证切片消费；库体本身可作 VC 目标）。**绝不**因为「它是库给的」而当通过（原则 3；「库自己写错 sanitize」是 §7-② 的不可消残留——本族能做的是把它变成一笔**显式记在账上的债**，不是消灭它）。

### §3.3 不允许隐式 declassify（if-校验旁路）

**控制流上的校验不构成净化**：

```
if is_valid(s) { sh_run_text(sh_text(s)) }     // s 仍是 string，不是 Sh<Text> ⇒ 仍拒
```

这正是本族相对经典污点分析的**结构性差异**：判据在类型项上，不在控制流上，因此不存在「校验函数没被建模 / 校验的是另一个东西 / 校验被短路」这一类旁路。若库希望让某个校验器真正放行，唯一途径是把它声明为**净化节点**（显式、可审计、带后置条件义务），而校验器若是**可能证不出**的谓词（如「完整 SQL 语法正确」），义务落 proof-required 而非 prove——**这正是义务阶梯的正确使用**，不是本族的失败。

### §3.4 净化节点与位置种类的判定边界

净化节点产出的是**新类型项**，不是新属性：`html_text: string → HTML<Text>` 成立的原因是**返回类型**，与 `trust` 标注无关（哪怕输入 `Trusted`，也仍是 `HTML<Text>`）。属性判据（裸位置）里没有构造器可用，因此那条路径上**没有**「位置化」的出口——只有 `declassify` 或改用已包装 API。这条不对称是刻意的：**类型判据优先，属性判据是退路**（§0 裁决 1）。

## §4 与既有机制的关系

### 4.1 与类型系统（R2）：同一个引擎，无第二套判定

- 位置形状项 `φ` = 类型项（R2 §1.2 `k(τ…)` / `AK_NAMED` 参数化命名）；判据 = `ty_sub`（R2 §3.2）；
- 形状满足 = R2 §2.5 `iface_satisfies` 同入口；
- 失败诊断 = `ty_witness` 给反例值（R2 §3.2/§7）；
- 常量档 κ = R2 §5.1 F11 三档约束项（先例：数组长度约束，P2a 已实施）。
- **不新增判定体系**（原则 4）：本族的全部判定是「把策略编译成形状项/约束，送进引擎」。

### 4.2 `string` 现状零标注 → 渐进引入（不破坏既有代码）

| 档 | 状态 | 判据 |
|---|---|---|
| 0 · 现状 | 无策略、无声明 ⇒ **无义务**（§0 裁决 9）；本族代码路径不进入 | 产物 **byte-identical**（同 R1/R2 「零回归锚」） |
| 1 · 审计 | 加载库策略；只报不拒（`--policy-audit` 式通道，默认关，两态产物逐字节同——**沿用 R2 `--type-shadow` 的先例**） | 审计清单产出；产物同 |
| 2 · 库级强制 | 策略声明语法位即拒绝；默认模式 | 正控绿 + 负控拒绝 + 回归全绿 |
| 3 · 高安全 | unknown/证不出 = 拒绝；`unsafe`/FFI 面须显式证明 | 未覆盖面登记为零静默 |

`string` 本身、既有函数签名、既有库调用**在四档中均不变**——变的是「是否存在声明的语法位」与「未处置义务的落法」。

### 4.3 与 S-A（属性轴 + 四档）

本族是 S-A 的**第一个消费者**，只消费不定义：用 `trust` 轴（裸位置判据）、四档决策树（§5）、policy 条目（§2.1）、诊断/台账通道（§3.2）。对齐锚点：S-A §1.1（`trust`：`untrusted ⊑ trusted`、来源 = 库声明 + 自动推导 + 净化节点）、§2.2（决策树与「违法 ≠ ④ reject」）、§3.1/§3.3（policy 条目与 `ty_sub(τ ⊓ A_a(v), Shape)`）、§4.3（enforce 失败语义）、§5.2（三面可见）。**S-A §9 五问待用户裁决**期间这些接口为暂行，裁定后本族随动一次（§8.2-9）。

### 4.4 与 where 三档（F11）

| F11 档 | 本族用法 |
|---|---|
| 常量档 | **解析式语法位**：文本形态（`sql_text`/`html_parse`/`sh_text`）要求实参编译期已知；恒假 ⇒ 编译错 |
| 符号档 | 位置相关的符号约束（如「表名来自白名单变量」）⇒ VC 义务（proof-required） |
| 动态档 | 允许落 enforce 的唯一场合：库提供**全函数校验器**（如标识符字符集 + 长度），校验失败 ⇒ **拒绝执行**（§5） |

### 4.5 与判定引擎的 unknown/预算

`ty_sub` 的 unknown（R2 §3.3 预算守卫 / P0 未覆盖面）在本族**不得当通过**：按 S-A §2.2 决策树落 ③ proof-required 或 ④ reject（strict），并**显式登记未覆盖面**。这与「不与类型不兼容混淆」一致——诊断要区分「确定不满足 ⇒ **违法**」（真非法边）与「未判定 ⇒ 未处置」（证据不足）。

### 4.6 与 S-B3（信息流族）的轴区分

本族消费 `trust`（不可信度，完整性方向）；S-B3 消费 `secrecy`（机密性方向）。**两者是不同轴**（一个防「坏结构进来」，一个防「秘密出去」），判据方向相反、残留不同（S-B3 的隐式流在这里没有对应物：本族对控制流免疫，§3.3）。本文不定义 `integrity` 轴用法，留给 S-B3/S-B4。

### 4.7 与 S-B2（授权族）的边界

「能不能执行 SQL」= 授权（S-B2，能力路径判定）；「文本能不能进 SQL 语法位」= 本族。二者正交：一次 `sql_exec` 可以「授权完备但非法边」（不可信文本 + 非法结构），也可以「文本合法但未授权」。**不得**用本族判据替代授权，反之亦然。

### 4.8 与 S-B4（围栏族）的边界

路径段既是**语法位**（`../` 改变路径结构）又是**围栏**（逃出 root）。本族判据说「不可信字节不能拼进路径语法位」；S-B4 说「无法构造指向 root 外的 capability」。`Path<Root>` 与 `φ` 的机制同族（形状项），边界 = 谁声明：路径**结构**的语法正确性归本族形态，**根约束**归 S-B4。重叠点登记为 S-B4 的输入（§8-开放问题 7）。

### 4.9 与载体（.ccr v7）的关系

形状项与位置声明**随库分发**才有意义（否则跨模块/预编译库丢失策略）。v7 段表已预留 `7+`（驱逐标注/证书段）——**是否新增 `POLICY` 段**、策略随 `.ccr` 走还是随源文件走，是实施批议题（§8-开放问题 5）；本族只要求「策略是数据、可随库携带、可被审计」。

## §5 义务落档

**本族主要在 ① prove / 违法**（对应路线图 S-B1 行「可证通过 / 拒绝」的主判）；unknown 面落 ③/④（S-A §2.2 决策树）；enforce 是受限退路；proof-required 只在净化后置条件与符号档处出现。

**术语前置（S-A §2.2 的两点关键区分，逐字沿用）**：「**违法**」= 引擎判定为**假**（已判定为不合法 ⇒ 编译错误，**任何 policy 档位都拒绝**）；「**④ reject**」= **无法处置**（判不出 / 不可强制 / 又不满足 strict policy）。本文表格严格按此分栏——**不要把「违法」写成「reject」**。

| 情形 | 落档 | 依据 / 落法 |
|---|---|---|
| 值位实参 | — | 无义务（`Shape(π)=⊤`，恒真） |
| `ty_sub(τ(v) ⊓ A_trust(v), φ)` = 真 | **① prove** | 零成本，不插入任何检查 |
| 常量档解析位 + 实参为编译期常量 | **① prove** | 档位判定恒真 |
| 常量档解析位 + 实参非常量 | **违法** | 档位判定恒假（不是运行时验证） |
| 语法位 + 实参项不满足 φ（引擎判**假**） | **违法** | 本族主判（非法边）；任何档位都拒绝；唯一放行 = §3 的净化节点（放行本身登记为义务） |
| 语法位 + 引擎 **unknown**（预算/未覆盖面） | **③ proof-required**（policy 允许）/ **④ reject**（strict） | **不得当通过**（原则 3）；登记未覆盖面（S-A §5.1 状态机） |
| 裸位置 + `⊢ Trusted(v)` 不可证（unknown） | **③ proof-required**（policy 允许）/ **④ reject**（strict）；若库提供全函数校验器且 policy 允许 ⇒ **② enforce** | enforce 失败语义见下 |
| 净化节点（`declassify` / 位置化构造器）的后置条件 | **③ proof-required** | VC 由验证切片消费；库体可作 VC 目标；证不出不静默（§3.2） |
| 符号档位置约束 | **③ proof-required** | 同 F11 符号档（S-A §2.3） |
| 库提供全函数校验器（标识符字符集、长度、白名单成员） | **② enforce** | 插入检查节点；失败语义按 S-A §4.3（默认 **abort** = 硬陷阱） |

**enforce 的失败语义（与 S-A §4.3 对齐后的精确表述）**：默认 = **abort**（硬陷阱，`IR_BOUNDS_CHECK` 先例）；S-A 允许 policy 显式声明 `degrade` / `report`，但本族**收紧一格**：

- `degrade` 在本族**只允许**把降级动作指向**库的净化构造器**（§3.1 位置化），即「校验失败 ⇒ 改走 `html_text`/`sh_quote` 这类声明过的节点」。理由：转义的正确性是**库的规格**（§7-①②）；若允许应用侧自写转义，等于把策略面偷偷搬回语言面（原则 2），并制造一个**没有台账条目的隐式放行**（违反原则 3）。
- 因此本族 enforce **不是**「变形器」，而是**闸门**或**闸门 + 库声明的净化节点**；`degrade` 目标须是策略 `declassify 通道`栏里的具名节点，且**记入台账**。

## §6 最小可实施切片

**切片原则**：切到「一个领域、一个形状项、三个构造器、一条判据、一组正负控」——不引入属性推导、不引入参数化判定、不引入 VC。

### 6.1 切片 1（本族首切片，判据完备可验收）

| 项 | 内容 |
|---|---|
| 领域 | `sql`（单领域） |
| 形状项 | 单一形态 `SQL`（**非参数化**，规避 R2 P3 参数化变型规则的未实施面） |
| 构造器 | `sql_text(lit /*κ=const*/) -> SQL`、`sql_param[T](v: T) -> SQL`、`SQL + SQL -> SQL` |
| sink | `sql_exec(q: SQL, binds: [SQL])`（槽 0 = 语法位，由**声明类型**承担） |
| 来源 | `io.read_file` / `cli.argv`（策略数据声明；本切片只需登记，供诊断文案与台账） |
| 判据 | `ty_sub(τ(实参), SQL)` + 常量档 κ；**仅此**（无属性判据） |
| 挂点 | 调用实参槽（checker 调用检查处）→ 引擎判定 → 诊断/台账 |
| 诊断码 | 建议新段 `EC_SF_*`（**段号与命名归 S-A 统一分配**）；至少区分：非法边（真不满足）/ 常量档未满足 / 未判定（证据不足，保守拒绝） |
| 依赖 | R2 P0 引擎（**已就位**）；形状项建表（`AK_NAMED` 具名项）；F11 常量档的通用化（见下）；S-A 的 policy 条目注册与诊断/台账通道（S-A §3.1/§3.5/§5.2——**共用，不另立**） |
| **不依赖** | 属性标注/属性传播（= S-A §6 切片所交付的面）、参数化原子判定（R2 P3）、VC（验证切片） |

**与 S-A §6 切片的关系（互补不重叠）**：S-A 首切片 = `untrusted ↛ system(cmd)` 的**裸位置 + 属性判据**路线（`os.cr` 的 `system`），交付的是轴标注/传播/义务流程；本切片 = **形状项 + 常量档判据**路线（`SQL<Structure>` 类型化构造器），交付的是领域库接口与构造器封闭。二者判据互补（属性判据 vs 类型判据），切片 1 **即使 S-A 的属性传播未就绪也可独立验收**；按路线图 §3.2 节奏，S-A 切片先行并落地共用通道，本族切片 1 随后挂上。

**正控（须通过）**：
- P1 `sql_exec(sql_text("SELECT 1"), [])` —— 常量档满足。
- P2 `sql_exec(sql_text("SELECT * FROM t WHERE x = ?"), [sql_param(read_file("u"))])` —— 不可信值走值位（bind），**这正是要保护的合法路径**。
- P3 `sql_exec(sql_text("..."), [sql_param(42)])` —— 类型参数实例化。

**负控（须判「违法」= 编译错误，且诊断为「语法位非法边」而非普通类型错）**：
- N1 `sql_exec(read_file("q.sql"), [])` —— 不可信 `string` 直落语法位。
- N2 `sql_exec(sql_text(read_file("q.sql")), [])` —— 常量档未满足（动态文本伪装成查询文本）。
- N3 `sql_exec(sql_concat(sql_text("SELECT * FROM "), some_runtime_string), [])` —— 拼接路径试图引入 `string`（`+` 无 `SQL + string` 重载 ⇒ 类型层无合法边）。
- N4 `sql_exec` 的实参是 unknown 判定（触发预算/未覆盖面）⇒ 落 ③/④ 并登记（**不得通过**）。
- N5 **属性项展开陷阱负控**（§1.2 注记）：构造一个「不可信值 + 值项 ⊓ 否定属性项」的组合，断言判定**不**因 `⊥ ⊑ φ` 而放行（防止判据被架空）。

**判据（验收门）**：
- **D1 零回归锚**：未加载策略时，全部产物 **byte-identical**（对齐 R1/R2 判据）。
- **D2 负控零漏**：N1–N4 全部拒绝，且错误码与文案落在语法位判据段（不是「类型不匹配」误报）。
- **D3 正控零误报**：P1–P3 全部通过；P2 的不可信值不产生任何附加检查代码。
- **D4 无特判**：编译器侧**不存在** `sql`/`html`/`sh` 标识符（grep 判据）；新增第二领域只需新增策略数据 + 形状项声明，代码零增长。

## §7 不承诺

路线图 §1.3 的三类**不可消**残留，逐条说明本族落在哪类：

1. **错误 specification**——Core 只能证明「程序忠实实现了规则」，不能证明规则本身正确。本族中**规则** = 库声明的「语法位集合 + 形状项 + 常量档 + 净化后置条件」。库可以把一个值位误声明为语法位（过度拒绝），也可以把语法位漏声明为值位（**漏保护**），或者把 `HTML<AttrValue>` 用在不安全的上下文中（§2.3 粒度不足）。**本族不可能消除错误 specification**：它是策略面的残留，不是语言能力不足。缓解 = 声明随库分发、可审计、可对照 §1.1 再扫描判据逐条自查。
2. **恶意/失陷外部实体**——供应链、编译机、密钥、硬件后门；用可复现构建/签名/provenance/最小权限**缩小**，不能用语言语义**证明**。本族中对应的具体形态是**库的实现**（TCB）：DB 驱动、HTML 转义函数、`sh_quote`、FFI 边界之后的代码。**本族不可能消除「库自己写错 sanitize」**——本族能做的是：① 让每一处放行**显式成节点**（可清点、可审计、进台账）；② 把净化正确性变成一笔**记在账上的义务**（§3.2，证明方式可后置）；③ 不把「库说了算」伪装成「语言证明了」。
3. **需求本身允许危险行为**——shell/browser/kernel/JIT 必须执行外来代码；目标不是禁止能力，而是**证明隔离边界**。本族中：程序**必须**接受不可信输入并**必须**把它交给解释器（否则程序无用）；本族证明的正是那条边界——「不可信值以**数据**身份到达解释器，且结构只能由**库的构造器**产生」。这与「shell 安全」不是一回事（§2.4 选项注入）。

**附加诚实边界（本族特有，不属上述三类但必须写在这里）**：

- **值位 ≠ 语义安全**：argv 值位只保证不改变结构，不保证参数语义无害（`rm -rf` 的选项注入；`--` 终结符约定）。本族判据**不覆盖**参数语义混淆。
- **编码层混淆不在判据内**：非法 UTF-8 序列、Unicode 规范化/同形字、大小写折叠（某些下游解释器不区分大小写）——这些改变的是**字节解释**，不是结构再扫描；归库的构造器（规范化后置条件）与 S-B3 之外的编码层议题。
- **未覆盖面**：引擎 unknown/预算耗尽会产生「证不出」；本族的处置是保守拒绝并登记（§5），**不承诺**「所有程序都能判定」。
- **本族的判定不替代任何下游安全机制**（授权、围栏、信息流、密码学）：见 §4.6–§4.8。

## §8 不做项 + 开放问题

### 8.1 明确不做（YAGNI）

1. **不做语言内建的 sink/source/领域关键字或漏洞类别特判**（原则 2 硬性；判据 D4 可检验）。编译器不知道 `sql`/`html`/`sh` 这些字符串是领域标识。
2. **不做完整污点分析作为主判据**：主判据是形状项包含（§1.3）；属性推导只在裸位置路径上，且属 S-A 的轴基础设施。
3. **不做转义正确性证明**：库的事（§3.1/§7-②）。
4. **不做流敏感/别名分析**：不需要（§1.2 末）。
5. **不做各语言语法模型内建**（元字符表、SQL 文法、HTML 上下文规则）——全部归库。
6. **不做运行时 escaping 作为默认落法**（§5 末）。
7. **不在本族定义 `integrity`/`secrecy`/`authority` 轴的用法**（归 S-B2/S-B3/S-B4）。
8. **不改 Graph 本体、不加关键字、不动命令式下限**（原则 1/5、定案 14）。

### 8.2 开放问题

1. **构造器封闭性的强制手段**：`pub` 今天不强制（`parser.cr:697` 写入无消费）⇒ 库外代码能否伪造形状项？选项：(a) 依赖「类型层封闭 + 库实现为 TCB」并在实施批论证用户无法伪造（本族当前立场）；(b) 实施库内可见性；(c) 策略白名单构造器集。**待论证**。
2. **属性项的展开约定（原「属性判据编码」——已由 S-A §3.3 收敛，余留一险）**：S-A 已定单式 `ty_sub(τ_value ⊓ A_a(v), Shape)`。**余留风险** = `A_a` 若以否定形式展开会产生 `⊥ ⊑ φ` 恒真的架空洞（§1.2 陷阱注记）——需在 S-A 实施批把「属性项以加约束形式单调展开」写成**规范性约定 + 负控**（本族 N5 为对应控）。
3. **F11 常量档的通用化范围**：现在是数组长度（P2a）；推广到「任意参数携带档位约束项」的改动面与判据（切片 1 硬前置）。
4. **隐式 declassify 的口子**：是否允许以 predicate-refinement（`where` 通道 + VC）替代显式净化节点？若允许，需评估 VC 质量与「校验器写错」的残留是否反而更难审计（§3.3 当前取「不允许」）。
5. **策略的携带形态**：随 `.ccr` 的 `POLICY` 段（v7 预留 7+）vs 随源文件的策略数据 vs 独立策略文件；跨预编译库分发的语义（否则跨模块丢策略）。与 S-A/R2 P4 载体批联合定。
6. **跨领域组合语义**：一个领域的输出成为另一个领域的输入（`sql_result → html_text`、`html → sql_param`）——位置化结果的类型项如何参与后续判据？是否存在「中转即洗白」的错觉？（预判：类型项携带形态参数即可表达，但需形态细分的配合。）
7. **与 S-B4 的路径重叠**：路径段既是语法位又是围栏；`Path<Root>` 与 `φ` 共用形状项机制，需要一条统一的分工判据（归 S-B4 输入）。
8. **未包装 API 的规模问题**：C 库/AOT/动态链接场景下裸位置数量大，策略维护成本高；是否允许（在审计档下）自动从符号/类型推断候选裸位置并生成清单供人工裁决——这仍属「策略数据生成」，不违反原则 2，但需要论证不产生「自动特判」。
9. **S-A 对齐余项**：本文已按 S-A 首稿对齐（状态行 + §1.2/§2.1/§3.2/§4.3/§5 五处锚点）。**仍待定**：S-A §9 五问的用户裁决结果、`Trusted` 判定入口名、policy 装载面、义务台账格式、错误码段分配（本文 §6.1 建议的 `EC_SF_*` 段号待 S-A 统一分配）。裁定后本族随动一次并记录差异。
