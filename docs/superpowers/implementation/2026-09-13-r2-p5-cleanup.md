### Task 1 根因与修法

报告为 `docs/archive/sdd/p5-task1-report.md`，证据在 `/tmp/p5t1b/`。

装载侧逐函数调用 `read_file(path)`，分配 `alloc(fsize+1)`。bump 分配器（`rt.s alloc`）不回收。946 个快照读缓冲累计 1.1674 GiB，超过 1 GiB 堆。堆定义在 `rt.s heap_start: .space 1024*1024*1024`。单条目最大 3,987,879B，即 3.80MiB，因为快照含全程序边表，尺寸是 O(程序) 而非 O(函数)。`alloc` 耗尽返回 0（`.Lalloc_oom`）。`load_cir_cache` 首行 `str_len(0)` 改为 `load64(0,-8)`，因此有缓存状态产生 SIGSEGV。gdb 三运行的调用顺序相同：`load_cir_cache` 调用 `str_len`，`str_len` 调用 `load64`，参数 `rdi=0`、`rsi=-8`。空缓存状态不读快照，因此 rc=0。

停条件核：写读对称表逐字段核对，覆盖字段、写偏移、读偏移、长度来源和 `pos` 推进。核对无长度域或格式缺陷，因此不 bump `CIR_CACHE_VER`，保持 17。

修法在根因层，不加钳位。`cir_cache.cr::cir_read_snapshot` 新增 30 行，使用单一复用读缓冲 `g_cir_read_buf` 和 `g_cir_read_cap`。峰值等于最大单条目。读侧自此与写侧既有的 `g_cir_write_buf` 和 `g_cir_write_cap` 同构。读侧原来是唯一逐调用新分的方法。`w64(buf,-8,fsize+1)` 保住 `str_len` 约定，因此消费面（`r64` 和 `str_sub` 四点）零改动。

载入失败条件为 `open` 失败、`fsize<=0`、短读、缓冲不可得（read EFAULT）、长度小于 56。此时返回 -1，表示 cache miss。三态纪律要求载入失败时拒绝，miss 是无害重建，绝不把错误当空表。刻意不写 `buf == 0` 形态的空判。该 `string-int` 混比在 bootstrap 侧 `x86_64_stack_asm.py:164` 编成 `str_eq(buf,0)`，所以 `str_len(0)` 自崩溃。建议另单，登记于报告第 6 节-1。

会报错的登记项如下。

- `string == int` 混比存在双路径分歧。bootstrap 使用 `str_eq` 分派。本修复绕开该问题，未修，建议另单。
- `g_cir_read_cap` 在 `alloc` 失败时仍前进，属于良性确定性。此后恒为 EFAULT，因此 miss，与写侧同形。
- 单条目超过 1GiB 的格式分片议题尚未处理。当前为 3.99MB，不属于本任务面。
- `.cir` 其余约定逐字未动，包括 VER=17、身份检查、指纹检查、项槽重派生和 save 侧。
