## 1. 判定 1：空行与注释行在 layout 里的地位

为什么它排第一：`[T0·实核]` `build_selfhost_native.py:154` 在列 0 插分隔符
`// === {f} ===`，把 45 档拼成 1 个编译单元；`:155` 用 `'\n\n'.join(parts)`；
`:157` 追加 wrapper 行。45 档拼接处若 layout 把下一个档的首行并入上一档，是不报错地错答案，不是 parse error。

### 1.1 判定（三条，每条唯一措辞）

1-1 空行（只含空白字符的行，含只含 `\r` 的行）：

1. 不产生任何 token；
2. 不改变当前 layout anchor；
3. 不参与「首个非空行建立 anchor」的计数。

1-2 只含注释的行（行内除注释外无 code；包括 `/* */` 块注释的续行、以及一行里只有多个注释的情形）：
完全等同于空行，1-1 的三条全部适用，一字不改。

1-3 行尾注释（形如 `code() // note` 或 `code() /* note */`）：
不改变该行的 anchor 列。anchor 列 ≡ 该行首个 token 的列（不是注释的列，也不是行首空白的宽度）。

### 1.2 由三条判定推出的两条结论（都已实测，见第 6.1 节）

结论 A（T3 必须知道）：拼接分隔符 `// === {f} ===` 的列不影响 layout。
由 1-2 直接推出，并已由 J-T0-1 的两格实测确认：分隔符在列 0 与在列 4 都得同一个结果（第 6.1 节矩阵第 1、3 行）。
因此T3 不需要为了 layout 把分隔符固定在列 0；固定在列 0 仍然是对的，但理由是「可读性」，不是 layout 正确性。

结论 B（真正的关键条件）：拼接分隔符必须保持「只含注释」这一属性。
一旦它不是注释行（例如变成 `x := 1`），它就成为一条真实的顶层语句，因此
拼接后的顶层声明数比两个档之和多出「分隔符条数」（第 6.1 节矩阵「非注释分隔符」格：35，37）。

### 1.3 对 T3 的硬约束（明确规定）

| # | 约束 | 检查 |
|---|---|---|
| 1 | 分隔符行必须只含注释（现行 `// === {f} ===` 满足） | J-T0-1 |
| 2 | 拼接的每一档内容仍须行级剥 `import `（`build_selfhost_native.py:150-153`），三处 concat 同改 | 计划第 5 节 |
| 3 | wrapper 行必须改成 v4 形（`build_selfhost_native.py:157` 是 f-string 发的 v3 花括号源） | 计划第 5 节（关键的一行） |

> 注意：约束 3 是拼接面唯一会让流程在第一步失败的一行：它是 Python 直接发出的 Core 源，
> 不经过任何语料改写。本档只登记它，不改它（T3 的工作）。

## 2. 判定 2：`:` 的双义消解

### 2.1 裁定：取 （b） 词法位置决定（唯一措辞）

> lexer 按「`:` 之后同一物理行内是否还有 token」发两种 token：
> 行尾 `:`，因此`T_COLON_BLOCK`（region 开启）· 行内 `:`，因此`T_COLON_DECL`（类型标注分隔符）。
> 这两种 token 的集合互斥且穷尽，因此parser 侧零前瞻。

原 `T_COLON`（`src/compiler/ast.cr`）由这两个 token 取代；`T_COLON_EQ`（`:=`）不受影响
（`:=` 是单个 token，见第 2.3 节的扫描：`:` 后紧跟 `=` 时不属于本判定）。

「行内/行尾」的精确判定（明确规定）：

> `:` 是行尾的 ⟺ 该 `:` 之后、到该物理行行尾为止，不存在任何 token。

空白不计；注释不计（见第 2.4 节）。

### 2.2 连带后果 1：「行尾的类型标注」的处置（唯一措辞）

> 规则：声明标注的 `:` 必须行内有后继 token；行尾 `:` 一律是 region 开启。

因此「行尾标注」这种写法不是本语言的合法文本：lexer 必然把它读成 `T_COLON_BLOCK`，
而该位置不是合法 region 头，因此parser 必须明确拒绝（`rc=1` + 诊断码，不得不报错地改判成声明）。
因此因此 （b） 的判别是完备的：`:` 的行内/行尾与 DECL/BLOCK 一一对应，规格不需要任何例外表。

逐形扫描（现行形 + v4 目标形，逐形给出 `:` 落在行内还是行尾）：

| # | 形 | 例（v4 目标形） | 该 `:` 的位置 | 目标出处 |
|---|---|---|---|---|
| D1 | 变量标注 | `x : int = 5` | 行内（Type 随后） | v4 第 4 节 |
| D2 | 标签形 | `count : int, mut = 0` | 行内（Type + `,` 标签随后） | v4 第 3.8 节 |
| D3 | 批量形 | `a, b : int = 1, 2` | 行内 | v4 第 4 节 |
| D4 | 字段形 | `id: int` | 行内 | v4 第 9.1 节 |
| D5 | 形参形 | `a: int` | 行内 | v4 第 8.1 节 |
| D6 | 形参表跨行 | `fn f(a: int,` ／ `     b: int):` | 第 1 行的 `:` 行内；终结 `:` 在续行行尾（region 开启） | v4 第 8.1 节 |
| D7 | import 别名 | `import math : m` | 行内（别名随后） | v4 第 2.3 节 |
| D8 | `mod` 路径 | `mod examples::pi` | 无单 `:`（`::` 是路径分隔符，不是 `T_COLON`） | v4 第 2.2 节 |
| D9 | 函数体开启 | `fn add(a: int, b: int) -> int:` | 行尾（有意 = region 开启） | v4 第 8.1 节 |
| D10 | 无体函数 | `extern fn read(fd: int) -> int` | 无 `:` | v4 第 8.1 节 |
| D11 | 接口方法 | `fn eq(&self, o: &Self) -> bool` | 无 `:` | v4 第 9.3 节 |
| D12 | lambda | `f := fn(x: int) -> int:` | 行尾（有意） | v4 第 5.4 节 |
| D13 | region 开启 | `if c:` `loop:` `match x:` `struct S:` `enum E:` `impl T:` `catch:` `unsafe:` | 行尾（有意） | v4 第 1.6 节等 |

反例扫描结果（`[T0·实核]`，命令见第 9 节）：零反例。

| 面 | 规模 | 行尾 `:` | 其中「声明标注」 |
|---|---|---|---|
| 现行语料（v3） | 227 档 `.cr` | 0 | 0（v3 用花括号开 region，连 region 开启都没有行尾 `:`） |
| v4 目标（原档的 core 代码块） | 77 个块 | 57 | 0（57 处逐处是 region 开启：`fn`/`struct`/`enum`/`impl`/`match`/`catch`/lambda/`spec fn`） |

因此规则无需例外。D1–D7 的 `:` 后面语法上必有 Type / 别名 / 标签，
所以「行内」是语法强制的，不是书写风格问题；若作者把 Type 写到下一行，那段文本非法（明确拒绝）。

> 注意：一处必须写明的实现风险（扫描发现）：形如
> ```
> fn f(a:
> int):
> ```
> 的形参标注断行，lexer 层无法与 `fn f() -> int:` 的头部终结区分
> 两者都是「`fn` 开头、行尾 `:`」，lexer 只看位置，因此两者都发 `T_COLON_BLOCK`。
> 这个形态的正确处置不是「让 lexer 做更复杂的判断」，而是由语法层处理：
> parser 在形参位期望 `T_COLON_DECL` 却拿到 `T_COLON_BLOCK`，因此报错（正是第 2.2 节规则要的「明确拒绝」）。
> 因此lexer 不需要括号配平，规格也不要求它配平（这是方案 （b） 成本较低的原因）。
> 「括号是否配平」只是本档探针在离线判定时用来把这一种情况从「合法头部终结」中筛选出来的方法
> （见 `tools/v4_layout_probe.py` 的 `_balanced`），不是给实现的约束。
> 因此检查 J-T0-2b 的族一夹具里就有这一格，且它必须失败。

### 2.3 连带后果 2：行尾判定必须穿过行尾注释（与判定 1 对齐）

> 规则：判「行尾」时，从 `:` 之后跳过空白与注释；若再无 token，因此行尾。

| 输入 | 判定 | 结果 |
|---|---|---|
| `fn f(): // note` | `// note` 是注释，因此不计 token，因此无后继 token | 行尾，因此`T_COLON_BLOCK`（region 开启） |
| `x : int = 5 // note` | `int` 已是后继 token | 行内，因此`T_COLON_DECL` |
| `fn f(): /* note */` | 块注释，因此不计 token | 行尾 |
| `fn f(): /* note` ＋ 下一行 ` more */` | 跨行块注释：`:` 之后到该物理行行尾只有注释字符 | 行尾（region 从注释结束后的首个 token 起算） |

与判定 1 的关系：同源，无冲突。 两条规则出自同一条原理，注释不是 token：

- 1-3 说「行尾注释不改变该行的 anchor（anchor = 该行首个 token 的列）」；
- 2-2 说「注释不计为后继 token」。

因此二者是同一原则在两个位置的应用，不冲突。

但有一处必须点明的交互（不掩盖）：1 与 2 用的「注释」概念必须同一份实现。
因此明确规定的实现约束：lexer 里 1 的 anchor 计算与 2 的行尾判定必须共用同一个
注释/字符串感知扫描器（`//`、可嵌套 `/* */`、以及「字符串与字符字面量里的 `//` 不是注释」）。
两处各写一份，因此两条规则必然漂（本仓已有同槽不同义的前科）。

再一处交互（顺带明确规定，因为它跨两个判定）：判定 3 的「紧邻其前」按 1 判定之后数，
空行与只含注释的行不插入到「紧邻」关系里。例：

```core
text := read_file(path)
// 准备配置
catch:
 | FileNotFound => fail "config not found"
```

因此`catch` 仍绑定紧邻的可失败语句 `text := read_file(path)`（注释行是 no-op，不打断紧邻）。

## 3. 判定 3：`catch` 的绑定对象与 layout 层级

### 3.1 绑定规则（唯一措辞）

> `catch` 绑定「同一 layout 层级内、最邻近其前的那一条可失败语句或声明」，
> 绑定的是那条语句/声明整个，不是它内部最深、或词法上最靠近的某个子表达式。
> 该语句/声明的值取恢复分支给出的替代值。

依据：v4 第 6.2 节两句话的交集。`catch:` 与被处理语句同层（`v4-syntax-raw.md:541`），
且「绑定到紧邻其前的可失败表达式或语句」（`:557`）。两条合起来唯一确定的读法就是本条的措辞：
取「同层」限定「紧邻」。

推论（明确规定）：`catch` 的有效前件只在同一个 sibling 组里找。
若同层紧邻的前一条语句不可失败，则 `catch` 是错误（不是「继续往上层找」）。

### 3.2 回填时序（明确规定）

parser 看到 `catch:` 时，被绑定的声明节点已经建成，因此必须回头把 initializer 槽包进错误边包裹器。
语义是 `cfg := (parse_config(text) catch …)`。

| # | 时序约束 | 理由 |
|---|---|---|
| 1 | 回填必须在解糖（`desugar`）/ 常量折叠（`pass.cr`）之前 | 否则回填落在已被优化的树上 |
| 2 | 回填必须在语句边界判定之后 | `;` 退场后边界由换行/缩进给出 |
| 3 | 回填必须在 region 结束判定之前 | 否则 `catch` 被当成 region 结束信号 |

因此三者的相对次序明确规定为：语句边界判定，`catch` 回接，region 结束判定，解糖，常量折叠。

### 3.3 用例表（至少 3 个，含计划的歧义反例；每条给期望绑定）

C1，同层紧邻声明（计划第 6.2 节首个例子，含空行）

```core
fn load_config(path: string) -> Config:
    text := read_file(path)
    catch:
     | FileNotFound => fail "config not found"

    cfg := parse_config(text)
    catch:
     | ParseError => fail "invalid config"

    validate_config(cfg)
    return cfg
```

- 期望：第 1 个 `catch` 绑定声明 `text := read_file(path)`；第 2 个绑定声明 `cfg := parse_config(text)`。
- 空行不改变绑定（由判定 1-1）：第 1 个 `catch` 与 `cfg := …` 之间的空行是 no-op，`catch` 组仍是 `text := …` 的后置子句。

C2，歧义最小反例（计划第 3.3 节；`catch` 与 `loop` 同列）

```core
fn f():
    loop:
        do_thing()
    catch:
     | E => break
```

- 期望：绑定 `loop` 语句（整个 `loop:` 语句），不绑定 `do_thing()`。
- 理由：`do_thing()` 的定位点列比 `loop:` 深，因此它在 `loop` 的 region 内，与 `catch:` 不同层；
 `catch:` 与 `loop:` 同列，因此同层，因此同层内最邻近的可失败语句 = `loop`。

C3，替代值形（`catch` 给值）

```core
cfg := parse_config(text)
catch:
 | ParseError => default_config()
```

- 期望：绑定声明 `cfg := parse_config(text)`；`cfg` 的值 = `(parse_config(text) catch | ParseError => default_config())`。
- 这是第 3.2 节回填时序的检查用例（`cfg` 的 initializer 槽被回头包裹）。

C4，未匹配错误继续传播（绑定 `_` 与绑定标识符）

```core
value := operation()
catch:
 | KnownError => recover()
 | e          => log_and_fail(e)
```

- 期望：绑定声明 `value := operation()`；`_` 匹配任意错误，标识符模式绑定错误值；
 `operation()` 的其余错误不被该 `catch` 捕获，继续自动传播（`v4-syntax-raw.md:575-577`）。

C5，同层紧邻者不可失败（负例）

```core
fn g():
    x := 1
    catch:
     | E => break
```

- 期望：错误（`x := 1` 不可失败，因此同层内没有可绑定的可失败语句）。
 不得向上层找、不得不报错地把 `catch` 当作空语句忽略。

### 3.4 J-T0-3 的正反两条断言

- 正向：C1–C5 的期望绑定逐条成立。
- 反向（本案的鉴别力证明）：把第 3.1 节的规则换成另一读（「绑定词法上紧邻其前的可失败表达式」）
因此C2 的结论必须翻转：从 `loop` 变成 `do_thing()`。
 C2 是唯一能分辨两读的用例（C1/C3/C4 两读同解，C5 在另一读下变成「绑定 `x := 1` 的 initializer `1`」，
 仍不可失败，因此仍错误，故 C5 不是鉴别用例）。C2 不翻转，因此J-T0-3 退回重写。

## 4. 判定 4：struct 字面量

### 4.1 判定（唯一措辞）

> v4 的 struct 字面量形 = `Type { field = value , ... }`
> （`{ }` 是字面量定界符，不是块结构；块结构已由 `:` + 缩进取代）。
> 字段分隔符必须是 `=`；`:` 形在整个语言里不存在。

## 5. 判定 5：洞内 `tokenize` 的缩进基准

### 5.1 事实与危险

`[T0·实核]` `src/compiler/parser.cr:433-450` `interp_parse_holes()`：字符串插值的洞内文本被
重新 `tokenize()` + `parse_expr()`，注释逐字自陈「必须在 token 流用毕后调用（会覆盖 `g_tokens`）」。

危险：layout 的 INDENT/DEDENT 是上下文相关的（缩进栈依赖「当前在第几层」），
而洞是从源里切出的一小段表达式（如 `n`），没有 layout 上下文，因此会产生伪造的缩进状态；
且洞内嵌套插值会递归重入。

### 5.2 判定（本档选 (b）：显式旁路旗标）

> 判定：在该路径上显式旁路 layout 发射。
> 新增全局 `g_layout_bypass`（int，通用约定：0 = 发射 INDENT/DEDENT（默认，fail-closed）；
> 1 = 不发射，且不读不写缩进栈）。所有「调用后不进入 layout 消费者的 `tokenize()` 调用点」
> 必须传 1。

规则（可机械判定，不留「视情况」）：

> 一个 `tokenize()` 调用点必须传旁路 ⟺ 该调用之后，在同一控制流里该 token 流不由
> `parse_all` / `parse_expr` 消费。
> （⟺ 它只做转储、重扫、自测、LSP 分析，或是重入路径。）

### 5.3 选 （b） 而非 （a） 的理由

1. （a） 的「规定基准列」在它要管的地方不可执行：洞文本是源里切出的一段，
 「强制以列 1 为基准」要求 lexer 按一个合成列重新编号，那就是一个「列原点」参数，
 本身就是旗标，只是隐式、且在调用点看不出来（正是要防的不报错地形态）。
2. （a） 不阻止发射：洞文本自身若含缩进（多行洞、或以空白开头的洞），
 缩进栈照样被写，因此（a） 把问题挪位，没有移走。
3. （b） 在本文件里已有同款先例：`g_parse_no_struct_literal`（`src/compiler/parser.cr:11`）
 就是「在重入路径上用一个模式旗标抑制贪婪分支」，
 复用仓里已确立的模式，优于为同一类问题发明第二套约定（也是第 0.4 节「同槽/同值不同义」纪律要求的先例核对）。
4. （b） 使 J-T0-5 的零构建那一半成为机械可判（第 6.5 节）：检查变成「每个无 layout 上下文的调用点都传了旗标」，
 读调用点即可判，不需要跑编译器。

## 10. T4 施工期补遗（本档第 1 节–第 5 节五条判定未覆盖的三面）

> 本节的来历：第 1 节–第 5 节是从「语料里已有的 `{}` 形状」反推 layout 规则；三面都不在
> `{}` 的射程内，因此 T4 实现时才现形。本节的每一条都带施工期实测读数（标注规则同第 0.2 节：
> `[T4·实核]` = T4 施工时实测）。
> 地位：本节是第 1 节–第 5 节的补遗，不是替代；与第 1 节–第 5 节冲突时以本节的裁定为准（维护者已裁）。

### 10.1 括号外的续行在 v4 不合法（`[T4·实核]`）

v4 的换行只在括号外构成 layout 断点：`()` / `[]` / 结构体字面量的 `{}` 内是隐式续行
（`bootstrap/corec/frontend/lexer.py` 的 `bracket_depth == 0` 检查）。括号外把一条语句
拆成两行（行尾是二元运算符，或次行以二元运算符开头），因此次行首 token 列更深，因此发 INDENT，因此
parse 当场失败。实测：

```
if a == 0 ||            ← 行尾 `||`
   b == 0:              -> SyntaxError: Unexpected token
```

因此语料迁移（T4/T6）必须把这类续行并成一行。语料里有真站点（如
`src/compiler/project.cr`、`src/compiler/module.cr` 的条件式；`[T4·实核]` 逐档计）。

### 10.2 空 region 在 v4 无法表达（`[T4·实核]`）

region 的语法要求至少一个 token（`_expect_region` 吃 COLON_BLOCK，NEWLINE，INDENT），
所以「`{ }`」与「只含注释的块」在 token 面不可区分，都是「region 无 token」，因此parse 失败：

```
fn f() -> int:
    // nothing          -> SyntaxError: Expected INDENT, got EOF
```

维护者裁定（2026-10-11）= 逐处改写，不扩语法面：
- 无 `else`、且条件无副作用的 `if … { }`，因此整条删掉（`src/compiler/interp.cr` 的
 `if op2 == 33 { }` 一类即此类：条件只读局部量）；
- 函数体只含注释，因此保留注释 + 补一条与声明返回类型匹配的显式 `return`；
- 其余形态（循环体空、`else` 分支空、声明体内的空 region），因此逐处上报裁定，不得自行拍。

不予采纳的两条（记录，防后人重走）：1 region 内塞一个 `unit` 占位，`unit` 是类型名，
当 no-op 语句用是 v4 文档没有的面；实测 `Parser(Lexer(...))` 虽接受 `unit` 作语句，但语义上是
「一个类型引用」而不是「空操作」，属绕过；2 把「region 可空」写进规格并改两个前端，改动面最大。

### 10.3 region 作声明右值：已裁定支持（`[T4·实核]`）

`unsafe` 在语料里有「作实参/右值」的用法（`b := read_file(unsafe { @str_of(...) })`）。
v4 里 `unsafe` 是 region（语句位），而实参位是表达式位，因此直接塞进去不是合法文本
（lexer 在括号内不发 layout，region 永远等不到 INDENT）。实测 `f(unsafe: …)` 必 FAIL。

维护者裁定（2026-10-11）= 支持「region 作声明右值」：声明的右值可以是一个 region，
其值取该 region 的尾值（与函数体同规则：只有最后一项是值）。于是
`x := unsafe: <E>` 成立，语料侧的 `f(unsafe { E })` 由 T4 机械上提：
先 `t := unsafe: <E>`，再把原处的 `unsafe { E }` 换成 `t`。

- 实现 = `bootstrap/corec/frontend/parser.py` 的 `_at_line_end()` 增加第三态：
 「prev == DEDENT 即行边界」（region 结束后 lexer 已把下一行首 token 接在 DEDENT 之后）。
 少了这条，`x := unsafe: …` 会在 `_end_decl` 处被误判成「同行还有 token」（`[T4·实核]` 复现：
 `expected end of line, got 'return'`）。
- 反向仍不成立：`f(unsafe: …)`（region 进实参位）依然不是合法文本；需要时先绑名字。
- 目标语法文档同步：`docs/developer/syntax.md` 第 4.1 节。
