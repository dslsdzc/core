## 0. 背景与定位

### 0.1 起因

HIT M2 实施（表驱动发射结束）在 Task 3 停摆：branch 模板形态（spec 两步 cmp+jcc，旧发射器实际四原子 load+test+je+jmp）、ret 事件（裸 C3，旧路径 IR_RETURN = 值序列加 jmp 到 epilogue 加 ret_patch）连续暴露计划级矛盾。排查结论：矛盾只是现象，模板在逐字节复刻一个本身是经典形状的旧发射器。这暴露出更上层的问题：转换编码层（corearch）与经典计算机绑定太深。

### 0.2 定性（2026-09-09 用户确认）

1. .ccr（格形态）大体成立：图坐标 NOD 加 REG 嵌套加 ENT 存在结构，方向正确，不推翻。
2. .ccr 局部不纯：NOD 语义仍为 v5 变量槽指令（load/store 字节槽、变量 = 可寻址位置而不是条目 × 版本）；ENT 恒空（存在结构 = 侧表，未成为主干）；处在“格不重新引入程序顺序”检查的边界上。
3. 真正的问题在转换编码这一层（corearch）：结构把经典机形状硬写进转换器逻辑，包括槽到 rbp 帧公式、寄存器分配、ABI 分派、tag/2L 编码选择、call/ret 控制栈、ELF；降低器（lower_to_core：IR 到槽操作加栈控制事件）同样按经典形状设计。
4. 表驱动（HIT/M2）只数据化了最后一段（指令字节），经典机绑定在转换器中段（帧/ABI/调用/降低）完全没有改动。本 spec 把实例化边界推到它应该在的位置。

### 0.3 本 spec 的权威用法

任何格式字段、模块、算法、计划任务，都可以用本 spec 的检查问四组问题（第 1 节），按审计方法（第 2 节）和契约规则（第 3 节）判定归属。裁决结果先于新工作：M2/HIT 后续任务、corearch 重写、v7 方向、第二维护者的横向扩展，凡涉及层归属的都必须能回答“格语义对象、实例数据、实例算法、泄漏待归一”。

## 1. 检查完备化（可逐类判定的准则集）

四组检查从既有定位点推导。每组末尾给出判定问题，对任意对象可逐条作答；任何一条答“是泄漏侧”即进入 G4 类型学点名。

### G1 语义本体检查（缓存语义七条的判定形态）

定位点：`docs/memory-model.md` 第一节（值 = 方法 / 驱逐不变量 / 再生等价 / 边界公理 / 赋值 = 版本化 / 地址 = 映射 / 映射实例正确性）加无方法条目统一规则。

判定问题：

1. 方法性：该对象有方法吗（可由 (产生它的图节点, 输入边) 再生）？驱逐它、保留方法，可观测语义会变吗？
2. 赋值形态：赋值表达为版本创建/失效/绑定移动，还是内存单元修改？
3. 位置形态：位置语义 = (条目标识, 偏移)，还是字节地址？
4. 身份形态：身份 = 产生节点（图节点身份），还是独立存储事实？
5. 边界形态：无方法条目（边界/图内不可重算）是否按统一规则处理（不按范式枚举）？

### G2 层形状检查（格层形态的充分条件）

定位点：capability-lattice v4 第 4.2 节（格不重新引入程序顺序。传统 IR/SSA/LLVM 本质仍是“另一种程序”，按执行路径组织，这是三层链成立的关键检查）、第 4.5 节（规则封闭对象开放）、第 4.6 节（无格承诺）。

判定问题：

1. 程序顺序：该结构是否按执行路径组织（文件序/指令序 = 执行序）？若序只是图的合法拓扑序列化（图语义完整可重建），判为“序列化”，不判为“程序顺序”。检查是语义实现方式是否完整，不是文件是否线性。
2. 范式枚举：规则/判定是否按范式枚举？层本体规则封闭（永不新建），对象开放（无界）。
3. 条目泛型：判定是否操作“条目”类别（位置 + 方法 + 存在）而不读值内容？
4. 最弱理论：语义是否写在比具体格代数更弱的理论里（共存 = 对称关系即可，无传递性承诺）？

### G3 实例/参数检查（编码层内容的合法形态）

定位点：z-vision 三层映射链（编码 = 物理编码空间，把格编码成具体机器的地址、字节、指令、位模式；编码层绑定经典机 = 合法且必须）、capability-lattice 第 11.5 节（寄存器分配 = 缓存语义映射实例，已接纳先例）、第 4.6 节（具体格代数 = 映射参数）、memory-model 第二节（区域/arena/字节权限 = 经典映射实例）。

判定问题：

1. 可换性：换平台（目标机/范式实例）时该内容语义会变吗？会变 = 映射参数或实例数据；不变 = 该内容属于格层；“换不掉且硬编码在通用机制里” = 泄漏。
2. 先例类推：是否与“寄存器分配 = 缓存语义映射实例”同族（对缓存语义的机器侧资源决策）？同族则按实例化处理，先例已接纳。
3. 参数形态：具体代数/组织（乘积格、ABI、帧序）是否作为映射参数存在，而不是层本体承诺？

### G4 泄漏类型学（点名用分类）

经典绑定泄漏的四种形态，审计与契约规则引用此分类：

| 类 | 名称 | 定义 | 典型表现 |
|---|---|---|---|
| 1 | 存储形状泄漏 | 变量 = 可寻址存储位置（帧槽/字节内存操作）进入格语义层 | load/store 字节槽、变量 = 内存单元、`&x` = 字节地址 |
| 2 | 控制形状泄漏 | 经典控制流形状进入格语义层 | 函数 = 可调用子程序、标签/跳转、栈 call-ret、行式执行序 = 语义 |
| 3 | 编码选择泄漏 | 目标机编码选择固化进格格式/转换器通用机制 | tag 字节布局、2L 堆指针表示、jo 溢出链、imm 宽度选择 |
| 4 | 平台惯例泄漏 | 平台惯例出现于格层或转换器核心 | ABI 寄存器分派、参数栈序、ELF/rodata 布局、调用约定 |

判定规则：G1-G3 答“泄漏侧”的对象归入 G4 类别点名；归入后按第 3 节契约裁决去向（实例数据 / 实例算法 / 入口归一化）。

## 2. v6 审计裁决表

审计对象 = `.ccr` v6 格式的设计语义（以 `2026-09-05-lattice-ir-v6-format.md` 为基础，v6 spec 自身明确说明若干妥协，见下）；实现现状差异单列注记（第 2.6 节）。格式 = 逐成分 × 检查得到裁决。

### 2.1 格式结构（Header/段表/坐标体系）：格侧成立

- 段表组织/变长记录/字节宽 = 编码层事务（v6 spec 第 7 节开放点自认；G3-1：换编码空间可调），不构成格层问题
- 坐标 = NOD id（图坐标）（D1）：存在区间端点/region 边界/定值点全部以图节点序为坐标，与 .cir 同坐标系，实现“图 = 唯一真相层”的坐标承诺，格侧成立
- 版本化只支持 v6、无转换工具：管线中间产物定位，可以

### 2.2 NOD（节点表 = 图事件 = 方法实现方式）：方向成立，语义带泄漏

- 实现方式形状：NOD = 图事件（每个节点 = 方法：op + dest/srcs + 类型码 + 边），符合格层本体规则 1“值 = 方法”的实现方式承诺，正确
- op 语义：NOD 的 op/dest/srcs 语义与 v5 instrs 相同（v6 spec 设计原则 6 明确说明：变量槽模型保留，为 corearch 最小改动）。这是显式妥协，不是原则性决定：
  - 1 存储形状泄漏：变量 = vars 表 id = 槽；LOAD/STORE/LOAD_FIELD/LOAD_INDEX… 的语义 = 字节内存操作（G1-3：位置 = 字节地址形态）
  - 2 控制形状泄漏：JUMP/BRANCH/LABEL/RETURN/CALL = 行式控制流形状（G2-1 边界）；REG 提供嵌套，但 op 语义仍按执行路径组织
  - 3 编码选择泄漏：tag/2L 相关 op 与帧 tag 语义出现在 op/类型码面（G3-1：换平台编码选择被当作 op 语义）
- 正面先例：ENT 版本化规则对 STORE 的勘定（定值目标在 s1，ρ(s1):=ρ(s2)，v6 spec 第 3.4 节），这是“赋值 = 版本化（规则 5）”的正确语义雏形，审计底稿中作为格语义形状的参照
- op 全集裁决方法：逐 op 以 Task 0 盘点清单 3（ast.cr 编号 0-51 全分类）为底稿，按 G1-G4 裁决。裁决结果 = 第 4.1 节的输入表（本 spec 不逐 op 落表；新工作引用本 spec 时按第 1 节检查加清单 3 底稿执行，落表由引用者完成）

### 2.3 ENT（条目表 = 存在结构核心）：格本体正确形状，有两处问题

- 形状：条目 = (var_id, version, def_nod, 存在区间, home, flags)。“条目 × 版本 = 赋值规则 5 的直接实现方式”“位置 = (条目标识, 偏移) 规则 6 的位置形态”“身份 = def_nod（图节点）”。ENT 是格层本体在 v6 里最纯的成分。
- 问题 1：恒空，未成为主干。regalloc 移后端（2026-09-07）后 ENT 恒空（loader 空表语义支持、零 version bump），存在结构 = 侧表，实际主干仍是 NOD 线性流。
- 问题 2：home 字段的语义定位。home = 分配器回填槽位。裁决：home = 缓存语义映射实例的注记（与“寄存器分配 = 缓存语义映射实例”同族；regalloc 移 corearch 后 -1 直通 = 已经在实例化方向上）。格本体最小集 = var_id/version/def_nod/区间/flags，home 可以保留，但语义定位 = 实例层数据。

### 2.4 REG（region 表）：格侧成立

SG 嵌套加区内条目范围 = 图绑定区域和共存推导的坐标实现方式（G2-4：共存不落盘、sweep 推导 = 最弱理论形态），格侧成立。区域 = 经典映射实例的组织面（memory-model 第二节），但 region 结构本身（嵌套坐标） = 图语义，保留在格侧是正确的。

### 2.5 NOD 边表缺席（v6 开放点 1）：格层纯度缺口

- 现状：边表在 v6.0 可以省略（文件序 = 合法拓扑序，重建无成本）
- 裁决：边 = 方法语义的必要成分（规则 1“(产生它的图节点, 输入边)”，缺边则方法不完整，“图 = 真相层”的文件实现方式不闭合，文件序退化为“另一种程序”的执行序，G2-1 从“序列化”滑向“程序顺序”）
- 是否落盘 = 编码层事务（v6 spec 第 7 节开放点 1 的编码层定性正确）；语义存在性 = 格层必需。格形态的纯度检查：文件必须能重建图语义（含边），执行序只是图的一个投影。

### 2.6 实现现状注记（本 spec 裁决为格式设计层；代码现状以复核为准）

- v6 spec 头部声明“代码按实施计划推进”；regalloc 移后端记录：ENT 恒空、opt_meta 恒 0、first_ent/param_ents 恒 -1、loader 空表语义已支持
- NOD op 与 v5 instrs 的精确对应、边表是否实际落盘、tag 元数据是否在 .ccr 内：引用本 spec 做具体裁决前，以 ccr_io.cr / corec lower 阶段复核为准

### 2.7 产出：不纯点清单与纯度边界

不纯点（按第 1 节检查点名）：

| # | 位置 | 泄漏类 | 程度 |
|---|---|---|---|
| P1 | NOD op 语义 = v5 变量槽指令 | 1+2+3 | 结构性（v6 设计原则 6 的显式妥协） |
| P2 | ENT 恒空未主干化 | （本体缺位而非泄漏） | 结构性 |
| P3 | NOD 边表缺席 | （方法不完整） | 结构性缺口 |
| P4 | ENT home 混入格本体语义 | 实例注记定位不清 | 轻（语义定位裁决即可） |

纯度边界声明：本 spec 只定检查与目标纯度，不设计 v7、不改代码。P1-P3 的修复方向（NOD 方法语义化、ENT 主干化、边表语义必须）指向未来的格式演进，凡涉及格式重构的工作须先过本 spec 检查；“纯度边界内可修”（P4 类语义定位加不触格式的检查应用）可随时按本 spec 执行。

## 3. corearch 转换器契约

### 3.1 定位

corearch = 格到编码的投影器：把格语义对象（条目/版本/方法/区域）投影为具体机器的物理编码。它不是执行器：执行标注空间（FIXPT/模糊/oracle/BSS/CORE）属于图（execution-annotation-space.md）；“图执行契约”定义为图层事务（HIT spec 第 7 节 YAGNI 现状维持，本 spec 不推翻，仅确认：格到编码投影不需要理解范式）。编码层绑定经典机 = 合法且必须（z-vision 三层链），问题只在绑定形态（第 3.3 节 C3）。

### 3.2 C1：输入契约（纯格）

- 转换器输入 = 纯格形态：条目 × 版本（ENT 语义主干）加图事件/方法（含边，语义完整可重建）加区域嵌套（REG）加符号/类型信息
- 现状 .ccr 的泄漏（第 2.7 节 P1/P3）在转换器入口做归一化：把变量槽/字节操作形状还原为条目/版本/方法语义后再投影。泄漏不得作为转换器的输入假设向下传播（现状转换器把槽 = rbp 帧偏移当作输入假设，这是问题的机制形态）
- 归一化层自身的正确性检查 = 语义保真（还原后格语义 ⊇ 原形状可观测语义，引用缓存语义规则 7 的映射实例正确性方向）

### 3.3 C2：输出契约（实例形态）

- 输出 = 目标机物理编码（今日 x86 ELF）。经典绑定在实例层全部合法：
  - 实例数据：投影表/模板（HIT 表 = 正确实现方式方向，第 3.5 节 C4）
  - 实例算法：帧布局（prologue/epilogue/帧公式）、调用序列（参数拷贝/返回协议）、寄存器缓存映射（regalloc = 已接纳先例）、tag/2L 编码选择，全部为映射参数实例
- 实例算法推广先例：`regalloc-cache-mapping`（寄存器分配 = 缓存语义映射实例）是已接纳的实例化先例。帧布局/ABI/调用序列/tag 编码与寄存器分配同族（对缓存语义的机器侧资源决策，G3-2），同族必须同类处理：入实例层，不入通用机制

### 3.4 C3：转换器核心只含通用机制

核心允许（且只允许）：

1. 格语义到实例请求的通用翻译：版本到位置分配请求、共存到资源互斥约束（判定四条形态）、方法到指令选择请求、区域到存储区段请求
2. 实例注册/选择机制：目标机实例（数据 + 算法）的登记、校验、按需装载

核心禁止（= G3 检查的可执行形态）：帧公式、寄存器名、ABI 参数序、tag 位布局、调用序列、ELF/rodata 布局等硬编码进通用机制。凡现 corearch 硬编码处 = 泄漏点，去向 = 实例层。

### 3.5 C4：M2/HIT 裁决

1. 方向：HIT 表驱动 = 编码层实例数据的正确实现方式（“换表即换平台” = C2 实例数据形态的实现路线），不废弃
2. 定位偏差 1，检查错：M1/M2 的对照检查 = 表路径 ELF 逐字节等于旧发射器产物，服务对象错了。模板的正确性检查应为“格语义到实例的投影正确性”（行为/结构等价加映射正确性定理方向，缓存语义规则 7），不是复刻注定退役的旧发射器的字节（包括其偶然形态：冗余 REX 位、jmp rel 0、ret_patch 技巧）
3. 定位偏差 2，范围窄：M2c 数据化只覆盖单指令编码形态（清单 1），帧/ABI/调用/返回序列（清单 2 R1/R2/R7 等）仍留在代码里。实例化边界应覆盖全部实例算法族（R1-R12 按 G3-2 裁决：实例算法参数化进实例层；纯翻译机制留核心）
4. 具体现象消解：ret 裸 C3 矛盾、branch 模板四原子与两步文本的矛盾 = 旧字节复刻检查的必然产物。按本裁决重定检查后，模板 = 实例的正确语义序列，不再追旧字节

### 3.6 C5：挂账裁决

- “事件流/表数据入 v6 段（NOD op 与 HIT event_id 对齐）”（TODO 挂账）：裁决 = 事件流与表数据是编码层事务（x86 实例的投影内容），不入格形态段。格形态携带语义对象，不携带任何目标机的投影中间物；NOD op 与 event_id 对齐 = 编码层实例注册问题（实例数据引用格语义对象的方式），不是格内容

## 4. 应用指引

### 4.1 裁决流程（引用本 spec 的新工作）

1. 对象过 G1-G3 检查，泄漏则 G4 点名
2. 对照第 2 节审计表与 C6 总表：已在表则按表执行；未在表则按第 1 节检查落表（落表结果回填本 spec 注记）
3. 涉及格式演进（P1-P3 修复方向 / v7）则先出设计 spec 过本 spec 检查，再谈实现
4. 涉及实例化（M2 重定检查与范围 / corearch 重写）则按第 3 节契约规则 C1-C3 逐条核对

### 4.2 即时应置（M2 停摆注记）

- HIT M2a Task 3+（branch/call/ret 模板实施）挂起，原因 = C4 检查裁决前不扩大旧检查下的实施；复启条件 = 按 C4 重定对照检查（或用户另行拍板）
- M2 计划/spec 的“逐字节对照”“汇合消灭混合”等规则在 C4 裁决后的修订 = 引用本 spec 的后续工作

### 4.3 与“两条根基改造不得同时进行”（type-system-direction）的关系

本 spec 是边界定稿（检查 + 定位），不是格式改造：不启动 v7、不动主链；它给未来的格形态演进和后端重写提供裁决基准，使这类改造发生时不再以“最小改动”妥协（v6 设计原则 6 的教训）。
