性质：只读审计（零构建、零源码/测试改动；全部结论来自实读 + `grep`）。体例：照 `2026-09-16-preexisting-bug-ledger.md`。
来源：`criteria-strength-audit` 代理的检查强度审计全文（含 05:54–05:58「检查实现方式化」批写入磁盘后的状态修订）+ `plan-capacity` 代理的坐标实核。
扫描快照：审计对象 = 当日 23:21 前后的树；05:54–05:58 一批写入磁盘改变了数条结论与坐标（下文逐条标「已修 / 仍存」）。
缘起（实证）：seam 批 sd 助手三处漏 `REX.B`，`[r11]` 编码成 `[rbx]`，因此野指针 139；而当时的检查各自独立 `find`（一条查 `4c8d1d`、一条查 `f20f1003`），中间插坏字节照样全部通过，因此检查漏掉了实际缺陷。

## 0. 方法论条目（核心结论）

弱点形态：片段式字节检查（disjoint-fragment matching），同一段期望序列被拆成多个各自独立的 `find`/子串断言，片段之间的字节无任何约束。
- 检查实际断言的命题是「这些片段各自出现过」≠「这段序列连续出现」，因此片段间的插入/替换（多一字节、错一个 ModRM、换成等长异义指令）都不会变失败。
- 实证：seam 批三处 `REX.B`（现 `src/arch/x86_64/instr.cr:474/489/501` 注释：「漏它则 rm=3 变成 [rbx]，因此野指针 139」）；修复后 A1 检查已改为连续序列 + 精确 4B gap + REX.B 入列（表 A 行 A1 = 修正后的强形态）。
- 4 反例驱动（可操作自检问句，本节的要求）：新增或评审任何字节检查时，逐条自问：
 > 「什么坏实现能骗过这条断言？」
 答不出，因此该检查尚未被证明有效（不等价于「够强」）；答得出且真能骗过，因此弱检查（进表 B + 登记 TODO）。
 实现建议：将该问句写进检查所在测试函数的注释（一行即可，例：`# 反例自检：改 modrm_reg_role 能否骗过本断言？`），因此让「能否被坏实现骗过」成为写检查时的必答题，而非评审时才想起。
 本日教训（维护者原话）：检查弱的成因不在写得少，而在从未有人问过它能否被坏实现骗过。
- 强检查写法：1 连续序列断言（整条指令字节，含 `??` 通配位）；2 带定长 gap 的正则（`..{0,N}`，N 尽量小并写明理由，A1 即此形）；3 定位点 + 定长窗口（长度可变段用长度公式，如 A2 的 `text[m+1]==0x83 and text[m+2]==0xEC 到 text[m+3]`）；4 反例驱动：每条字节检查评审时须回答「什么坏实现能骗过它」，写不出反例 ≠ 强，写得出而检查仍通过 = 弱检查。

### 实证（决定性，2026-09-16）：apx 探针的声明形

apx 审计（`2026-09-16-apx-conversion-audit.md`）表 B 的十条探针源统一写作 `d : ., apx = 7.0;`（类型位用 `.` 推断 + `apx` 标签）。而 `ir_gen.cr:2388-2393` 的 apx 槽建立以 `declared_ti == TI_DEX` 为前提；类型位写 `.` 时 `declared_ti = TI_UNIT`（`:2377-2378`），因此 apx 分支整段不进，因此槽型回退 `TI_DEX_S`，因此 apx 标签对槽形式零作用，探针退化为普通精确 dex。
，因此该表十条全部误判通过：不是断言写弱，而是探针从未覆盖 apx 转换面。

判别法（本例，可机械执行）：
1. 产物形态自校验，`.cir` 中 `const dex = <binary64 位模式>` 序列的在场性（显式形：`const dex = 4619567317775286272`（7.0 的 bits）+ `_dxs`/`_dxm`/`_dxc`/`branch`/`_dxh`/`F2I` 序列；推断形：只有 `const dex = 7000000` + `store`）；
2. 反向自校验，`corec run`（解释器）在显式形下拒收 rc=255（`IR_I2F/IR_F2I` 无 binary64 语义，`interp.cr:263-266`/`:704-705`），推断形则正常取值，因此拒收本身就是「apx 槽确已建立」的证据；
3. 正面证据（数值反推执行路径），`bits(7.0) mod 2⁸` 与实测读数的逐例吻合（T1：`4619567317775 mod 256 = 15`，9 例同值），因此证出「bits 原样入槽 + 读点定型 `TI_INT` + `@raw_int` 无转换」这条链确实被执行。

### 通用判别法（写探针时的必答题，与 0 节的反例问句配对）

### 实证（追加，2026-09-16 检查集合加固批）：两条同族实例

本批把 0 节 bis 的问句用在检查自身上，当场识别出两条同族误判通过（均非推论，而是在改强过程中实测得到）：

实例 1：检查内部的 `sub` 分支从未被走到（`test_mw_task2.py` 慢路径块体模板，#85/B6）
- 事实：块体模板加了 `is_sub` 分支断言（sub 站点块内多 3B `49 F7 D3` = `not r11`），而原三例 `t1_add`/`t2_add_overflow`/`t3_bigfunc` 全是 add（`x + 1`/`x + x`），因此该分支在语料上从未被走到，断言即使写错也始终通过。
- 处置：加 `t4_sub_overflow`（`x = x - -4611686018427387904`，得到 2^63 正溢出），sub 版块被确实覆盖（`@O0/@O1/@O2` 三档 + 16B stdout 数值校验）。
- 判别法（可机械执行）：逐分支覆盖检查，把检查里每个条件分支（`if is_sub` / `elif name == "store"` / 事件 id 集合 / 行类型分类…）列出来，逐个问「哪条语料/哪个用例走到它？」；答不出的分支 = 该分支断言未被证明（要么补语料，要么在注释里显式登记「本分支未覆盖」）。

实例 2：fail-closed 解码器当场识别出「未登记指令形态」（`test_mw_task2.py` `x86_insn_len`，#90/B1）
- 事实：零 diff 检查组的检查侧长度解码器上线首跑即判为失败，慢路径块首 `4D 19 DB`（`sbb r11,r11`）的 opcode `0x19` 未登记（`_OP_MODRM` 漏了 `0x11/0x19` 两个 ALU 双操作数 opcode）。
- 意义：这正是「宁可失败不会无提示」的现场实证，若解码器当初写成「未知 opcode，因此当 1 字节放过」或「未知，因此跳过」，这条缺失项会无提示留在检查里（正是 0 节 bis 要消灭的形态）。fail-closed（未知形态，因此抛错，因此判为失败）把「未覆盖面」变成了「必须处理的显式事件」。
- 判别法（同族）：任何检查侧的「解码/解析/分类器」都应当 fail-closed：未登记形态，因此失败，而不是 `continue`/`pass`/默认值。检查的未覆盖面必须响，不得无提示。

### 0quater 「新增诊断 ≠ 修好」的成立实证（2026-09-16 #93 批）

机制：一次修改触发面（补实参推断）会同时带来两类结果，1 真修好（原本无提示的错被报出/被修）2 新引入误报（原本合法的写法被判错）。二者在「诊断计数」上不可区分，因此若用「新增诊断数上升」当修好证据，必然把误报一起记成修好。
