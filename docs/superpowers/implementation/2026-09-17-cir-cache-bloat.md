# `.cir` 快照缓存二次膨胀，只读侦查 + 实施计划（2026-09-17）（实施记录）

> 对应计划：[plans/2026-09-17-cir-cache-bloat.md](../plans/2026-09-17-cir-cache-bloat.md)

## 概述

本记录覆盖 `.cir` 快照缓存二次膨胀的 T2 实施与 T4 检查，以及只读侦查阶段的自检和方法论产物。T2 把每条函数快照的保存范围收窄到本函数的边，边引用改为 24B 相对 id，并在尾部加 trailer；装载侧改为先校验后恢复，恢复期由 `df_add_edge_kind` 重放重建。`CIR_CACHE_VER` 从 19 改为 20，新增 `tests/selfhost/test_cir_cache_narrow.py`。实测结果为冷态零影响，与修复前二进制在冷态和暖态下逐字节相同；缓存从 1.4 GB 降到 39.8 MB，冷态从 231 秒降到 39.77 秒，暖态从超过 254 秒被看门狗杀掉降到 32.50 秒，首次出现暖态快于冷态。五个 CI job 全部 rc=0，`selftest-types` 415/415，但 `full-bootstrap` 不控制缓存态的问题被登记为 TODO #2026-09-17-17。

## 改动

### 实现

源码面改动如下。`ast.cr` 增加 `g_df_func_edge_start` 声明。`dyn_arr.cr::grow_df_arrays` 做同域增长。`dataflow.cr::df_begin_func` 记录边起点。`cir_cache.cr` 的保存侧只写本函数的边，边引用使用 24B 相对 id，尾部写 trailer。装载侧先校验后恢复，校验包括结构预扫、载荷恰长、`var_start` 恒校验、越界 rel 条件见证、逐节点 `edge_count` 见证。恢复期把 `first_edge` 与 `edge_count` 归零，然后由 `df_add_edge_kind` 重放重建。

`CIR_CACHE_VER` 从 19 改为 20，另有 6 处实现方式同步更新。新增 `tests/selfhost/test_cir_cache_narrow.py`，包含 P1、P2a、P2b、P2c 和 P4。

### 装载必须两趟

装载必须先校验后恢复，这是正确性前提，不是风格问题。原实现边写边判。半途发现条目不可用，例如长度不符或见证失败时，全局数组已经被部分污染。调用方随后按「miss，因此重新生成」处理。生成会把新节点、新边和新变量追加到那份半恢复的图上，而 `g_df_node_count` 与 `g_ir_var_count` 已经推进。产物因此是「旧条目的碎片加新生成的实体」的混合图，属于不报错的错图类。两趟要求一切判定在任何写之前完成，装载要么整体成立，要么完全不动。P4 与截断面就是该设计的直接检查。

### 检查集合抓到的缺陷

`test_cir_warm_path.py` 的 D5 检查「补零条目仍须命中」，在本次首次运行失败。本次首版把 trailer 定位在 `dlen − 16`，并要求载荷恰好铺到 trailer 前。尾随字节因此被判 miss，既有契约被破坏。修正为 trailer 定位于结构扫描终点 `p`，只要求 `p + 16 <= dlen`。尾随字节容忍属于既有契约，截断仍然 fail-closed miss。修后 D5 通过，整套 19/19。

这条缺陷由既有检查集合当场发现，说明新检查 P4 引入的严格性必须与既有契约一致。这是回归检查的价值。

### 方法论三条

这三条在 2026-09-17 阶段 7 结束后写进文档，追加不重写。写法是结论、防止的具体事故、何时使用。三条同属一个主题：检查集合不只校验实现，也在修正实现，包括修正流程。写进文档的原因是这三条原先只存在于 PR #104 的描述里，而 PR 描述是仓库外的信道。方法论必须落在提交里，本仓先例是 spec-grammar 第 17 节。

方法论-1：检查集合修正实现。新实现引入的严格性必须与既有契约一致。既有检查集合报失败时，先按「谁破坏了既有契约」定性，不得先改检查。防止的事故是阶段 7 首版把 `.cir` trailer 定位在 `dlen−16` 并要求载荷恰好铺到 trailer 前，破坏了「装载容忍条目尾随字节」的既有契约，`tests/selfhost/test_cir_warm_path.py` 的 D5 立即失败。修法是 trailer 定位于结构扫描终点，要求 `p + 16 <= dlen`，容忍尾随字节，截断仍然 fail-closed。使用时机是给已存在的装载、解析或格式面加校验，或者改动语义边界与容忍度时；先运行既有套件，再谈新增检查。

方法论-2：检查集合修正流程。凡改 `TODO.md`、格式面或既有权衡约定，推前先运行对应本地检查。「本地检查通过」的复核点必须落在提交，即 `jj file show -r @ <file>`，不是工作副本。防止的事故是阶段 7 首推 PR #104 后 `bootstrap-tests` 在 6 秒内失败。解 `TODO.md` 冲突时把 jj 的 diff 残留标记 `+| …` 和 `+### …` 拼回正文，条目标题被前缀污染，`tests/harness/test_todo_id_migration.py` 的 J2「无悬空」报 5 处悬空。修法是剥前缀 16 行，推前本地运行 J1 至 J5。使用时机是每次 rebase 解 `TODO.md` 冲突之后（阶段 7 两次遇到）、任何批量文本改写之后、推 PR 前的最后一道自检。

方法论-3：本地通过不等于内容在提交里。本地检查读工作副本，CI 读推送出去的提交，两者可以分离。推送后以 CI 检查为准，本地通过只作预警。防止的事故有两个。第一是同族旁证，阶段 6 内容收敛后本地检查全部通过，随后 `jj edit` 或 bookmark 操作把合成内容从尖端提交带走，尖端丢内容，发现它的是 CI。第二是阶段 7 同族再现，`jj rebase` 遇到已合入的同段内容（#107 已进 develop）时产生「重复内容」冲突块，若照原样重推，等于回退已合入的语义。处置分三步：删冲突书签到 abandon 冲突提交；在 develop 上重建 delta；推前用 `jj bookmark list` 实查书签存在。使用时机是任何「大内容收敛、rebase、bookmark 迁移」之后，以及每次推送前的最终自检。

### E5 成对基线

本机背靠背运行，命令和环境相同。老二进制是修复前的 9-16 版，与本次只差本次改动。

| 项 | 修复前（老二进制） | 本次 |
|---|---|---|
| 空缓存状态运行 | 101.68 s | 47.53 s，2.1 倍 |
| 有缓存状态运行 | 194.58 s，未无响应，但仍慢于空缓存状态运行 1.9 倍 | 29.58 s，快于空缓存状态运行 1.6 倍 |
| 缓存 | 1,416,095,437 B（1.32 GiB），1013 条 | 39,764,757 B（37.9 MiB），1013 条，35.6 倍 |
| 空缓存与有缓存产物 | 无数据 | `cmp` IDENTICAL |
| 环境（读数条件） | loadavg 9.8 改为 10.9，MemFree 2.1–2.3 GB | loadavg 5.6 改为 8.0，MemFree 2.0–2.3 GB |

主要结论是从净负收益转为正收益。修复前有缓存状态运行慢于空缓存状态运行 1.9 倍，缓存没有收益。修复后有缓存状态运行快于空缓存状态运行 1.6 倍。

两个负载档并存，属于条件式。本表是轻载，修复前有缓存状态运行 194.6 s，没有无响应。重载档出现在阶段 6 与本次检查期，loadavg 12 至 18，伴随 swap 抖动。修复前有缓存状态运行超过 254 s 被看门狗杀掉，另一轮 13 分钟以上未完成。因此重载下「至少 7.8 倍」是下界，属于不可测值；轻载下为 6.6 倍，即 194.6 除以 29.6。

收益分两栏，不得混算成一个倍数。第一栏是字节项，1.4 GB 改为 39.8 MB，35 倍；首次运行该分项从 9 至 18 分钟降到 17 至 35 秒，本次消掉。第二栏是条目数固定项，1011 乘约 0.15 秒约 150 秒；该分项与字节量无关，本次不消，交 TODO #2026-09-17-16。因此空缓存状态运行收益等于写侧减量，即第一栏；有缓存状态运行收益等于工作集驻留（46 MB 远小于 RAM），条目按缓存态计价。

倍数约定有三条。第一，「31×」不进入表述，空缓存状态运行收益归写侧减量，有缓存状态运行收益归驻留，见上两栏。第二，「至少 7.8 倍」的「至少」必须保留，修复前有缓存状态运行是看门狗杀，不是可测值，因此只是下界。第三，读数随环境快照，loadavg 12.44 改为 12.49，MemFree 831 改为 1386 MB，机器未空闲，因此是条件式。

本次主要结论采用维护者裁定的定性表述，不写「小了多少」。`.cir` 缓存此前是净负收益，有缓存状态运行 13 分钟以上被看门狗杀，大于空缓存状态运行 231 s，并且无响应（D 态）。本次后第一次出现暖态小于冷态，即 32.50 s 小于 39.77 s，从「25 倍负收益」变为「正收益」。

### 自举链的缓存态

`full-bootstrap` 检查不控制缓存态，据实登记并做三重对照。

| 运行 | 前置缓存态 | 结果 |
|---|---|---|
| A | 实验残留 1,013 条，由 `build -O 0` 写入 | RED。corec2 为 2,934,398 B，不等于 corec3 的 2,916,990 B，`e_entry` 位移等于差值 0x4400。 |
| B | `selfhost-tests` 运行完 | GREEN |
| C | 紧接 B，检查可复现性 | GREEN |

干净缓存三重自证如下。执行 `clean-cache` 后，a1（冷态）等于 a2（全命中暖态）等于 a3（自建），都是 2,916,990 B，`cmp` 两次 IDENTICAL。因此命中路径与冷路径产物一致，自举固定点成立。

A 的失败状态签名是：两产物代码布局完全相同，`main at [1012] off=2873999 cp=2874175`，差异只在内嵌串。corec2 独有一组 `#check` 与 `#ensure` 注解诊断字面量，corec3 的独有集为空。因此构建期驻留串集合不同，不是代码生成分歧。
