## 〇、为什么计划长这样（(乙) 的三个后果，以及每个后果逼出哪一节）

> **维护者已裁决，本档不重新论证**：

**(乙) 在语法侧只说了「一次迁完」。它对**工程**的全部压力在下面三条后果里**——本档的每一节都是被它们逼出来的：

### 后果 ①：必须原子翻转 ⇒ **一个原子的批，不是一个原子的提交**

前端一翻到 v4，旧语法源**立刻编不过**。于是：

```
Python 前端读 v4（T1/T2）   ─┐
Python 发出的 Core 源改 v4（T3）├─ 这五件事任何一件单独做，链就断
自源写法改 v4（T4）          │
自源 reader 语义改 v4（T5）  ─┘
```

**⚠ 这是本档对 `mech.md` 的一处更正，也是本档最重要的一条结构判断**：

`mech.md §1.2` 把 T4 与 T5 排成两步，并在 T4 行写下「**`corec2 == corec3` 在此仍可跑**（自洽性与语法无关）」。
**这条在 (乙) 下不成立**：T4 完成时，`src/compiler/*.cr` 已是 v4 文本，而 `build/corec` 的原生 parser 仍是 v3 语义
（T5 未做）⇒ `corec2` 编不动 `src/compiler/main.cr` ⇒ **`corec3` 根本不存在，无从 `cmp`**。
⇒ 在 (乙) 下 **T1–T5 是一个原子批**：中间没有任何一个状态既「能构建」又「能读我们自己的源」。
（`mech.md` 的 T4/T5 可拆**只在 (甲) 双语法下成立**——而 (甲) 已被裁决排除。）

⇒ **本档 §四–§七 因此按「一个批、五个必做面」写**，而不是按「五步」写；
**但提交仍可分笔**（见 §二.4「二分定位」）。

### 后果 ②：链中间没有可构建态 ⇒ **第一个能构建的状态就是终态**

⇒ **「是哪一步坏的」在链上不可二分**（唯一能二分的两个点都在批外：批前、批后）。
⇒ 于是**定位能力必须来自批内**：每个必做面必须自带一条**不依赖构建**的机械判据。
⇒ 这逼出两样东西，它们是本档的第二等交付物：
- **§二.2 判据换代表**（批前采基线 → 批中挂起 → 批后重锁）；
- **§二.3 反向规范化对拍**：把 v4 文本**机械还原回 v3**并与改前逐字节比 ——
  **这是批内唯一能在零构建下判定「T4 只改了形状、没改语义」的机器**。

### 后果 ③：窗口内逐字节判据显式挂起 ⇒ **必须换一类判据顶上，且要写死是哪一类**

语法迁移**必然**改 `.ccr` 字节（STR 段 = 编译器全量 intern 表，按 intern 次序写）与 canary ELF。
⇒ 「逐字节不变」在窗口内**不可能绿**，而**一条注定恒红的判据不是判据，是噪声**。
⇒ 必须**显式挂起**它、**显式指定替补**、并在窗口后**显式重锁**。三件事都要写死次序（§二.1）。

### 2.3 **反向规范化对拍（B4）—— 批内唯一能在零构建下定位 T4 的机器**

> **它解决什么**：T4 要把 `src/**` 的 `{ }` 改成 `:` + 缩进、把 `;` 去掉。**这是纯形状改动**。
> 若有一个确定的**逆变换**，就能断言「改前 ≡ 逆变换(改后)」——**零构建、逐档、可机械化、可突变自证**。

**规格（写死，实施时不得即兴）**：
```
输入：改后的 v4 文本 F_v4
输出：还原的 v3 文本  F'v3
规则（唯一）：
  R1  layout region → `{` … `}`：按 anchor 关系重建花括号（同层 sibling 平铺，更深者入块）
  R2  换行分隔的语句/字段/臂 → 补回 `;`（**只补在改前有 `;` 的位置**，位置表由改前文本给出）
  R3  `none` ↔ `None`、`never`/`dyn` 的关键字化**不参与本变换**（它们是语义面，见 T1/T5）
判据：`cmp F'v3 <改前文本>` 逐档必须相同
```

⚠ **R2 依赖「改前的 `;` 位置表」——这是它的软肋，必须写清**：
- 若把「改前的 `;` 位置表」也作为输入，则 B4 **只能证明「形状变换没丢东西」**，不能证明「`;` 的删除是有意的」。
- ⇒ **B4 的正反两条断言（缺一不可）**：
  - **正向**：76 档（本判据面 = `src/**` 的 74 档七目录面 + 其余）逐档 `cmp` 相同；
  - **反向**：**故意把改后文本里的一个块结构改错**（例：把一个 4 空格缩进改成 3 空格 ⇒ anchor 关系变）
    ⇒ **B4 当场红**。**不红 ⇒ B4 是假判据，退回重写。**
- ⇒ **B4 的产物是一条脚本，不是一个「已看过」的结论**。它是本批**唯一**能在批内定位 T4 的东西（§二.5）。

### 3.1 T0 输入 ①：注释行与空行在 layout 算法里的地位（**最高优先，因为它决定自举链成立与否**）

**为什么它排第一**：`build_selfhost_native.py:154` 在**列 0** 插 `// === {f} ===`，把 45 档拼成 1 个单元。
v4 §1.6 说「空行与只含注释的行不改变 layout」⇒ 该分隔符对 layout 是 no-op，各档顶层声明在列 0 **天然互为 sibling**。
**但这**依赖注释规则被写死**。若规格改成「注释行参与缩进」或「注释行必须与相邻行同列」，
则 45 档拼接处会**静默吞掉下一个文件的首行**——**那是静默错答案，不是 parse error**（`[代读]` `mech.md §6.0`，我核了 `:154` 的确在列 0）。

**T0 必须给出的判定（三条，缺一不可）**：
1. **空行**：不产生任何 token、不改变 anchor、不参与「首个非空行建立 anchor」的计数。
2. **只含注释的行**：同上（**完全等同于空行**）。
3. **行尾注释**（`code() // note`）：**不改变该行的 anchor 列**（anchor 取该行**首个 token** 的列）。

**★ 并且必须有一条针对拼接场景的判据（当前不存在，本档要求新建）**：
> **J-T0-1（拼接 layout 探针）**：取**两档**已知文件，按 `concat()` 的规则拼（`'\n\n'.join` + 列 0 分隔符 + 行级剥 `import `），
> 断言：**拼接后的顶层声明数 = 两档各自顶层声明数之和**。
> **反向对照**：把分隔符**改成带缩进**（例：`    // === f ===`）⇒ 该判据**必须红**。
> **零构建可实现**（纯文本/计数）——它是 §十一 U-9「拼接场景判据不存在」的收尾。

### 3.2 T0 输入 ②：`:` 的双义消解

v4 里 `:` 既开 layout region、又是类型标注分隔符；现行 lexer 只有一个 `T_COLON`（`[代读]` `gap.md §17`）。

| **(b) 词法位置决定** | lexer 按「行内 vs 行尾」发 `T_COLON_DECL` / `T_COLON_BLOCK` | lexer 有状态更多，但 parser 更简单 |

### 3.3 T0 输入 ③：`catch` 的绑定对象与 layout 层级（**有真歧义，需维护者裁定**）

v4 §6.2 的两句话在**同一个例子**上给出**不同答案**：
- 「`catch:` 位于被处理语句的下一行，**与该语句处于同一 layout 层级**」⇒ 绑定**同层的上一条语句**；
- 「`catch` 绑定到**紧邻其前**的可失败表达式或语句」⇒ 绑定**词法上紧邻者**。

**歧义的最小反例**（`[代读]` `mech.md §6.2-2`，我核了这段规格文本确实两读皆可）：
```core
fn f():
    loop:
        do_thing()
    catch:
     | E => break
```
`catch` 与 `loop` 同列。**它绑定 `loop` 还是绑定 `do_thing()`？** 两者语义不同，**且错绑是静默的**。

**T0 必须给出的判定**：
1. **绑定规则的唯一措辞**（本档建议：**「绑定同层的最邻近一条可失败语句」**，因为它是两条规则的交集，但它**是建议，不是裁定**）；
2. **`catch` 的回填时序**：`cfg := parse_config(text)` 后接 `catch:` 给的是**替代值** ⇒ 语义是 `cfg := (parse_config(text) catch …)`。
   parser 看到 `catch` 时**声明节点已建成** ⇒ 必须**回头**把 initializer 槽包进错误边包裹器。
   ⇒ **时序必须钉死**：**在解糖（`desugar`）/ 常量折叠（`pass.cr`）之前**回填，否则回填落在已被优化的树上。
3. **`;` 退场后「可失败语句」的边界**由换行/缩进给出 ⇒ `catch` 的回接必须**在语句边界判定之后、region 收尾判定之前**做。

**J-T0-3**：规格必须给出**至少 3 个 `catch` 用例**（含上面的歧义反例），并**写明每个用例的期望绑定**。
**反向对照**：把绑定规则改成另一读 ⇒ 歧义反例的结论必须**翻转**（证明该用例真有分辨力）。
