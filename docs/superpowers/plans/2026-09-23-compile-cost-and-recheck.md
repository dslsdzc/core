## 〇、为什么计划长这样

三步的依据，逐条写清：

1. `[评估·推理]` 那套 8 项元编程模型「现在能做 = 0 项」，共同的、最小的前置（「编译期元对象」这一层的表示）

   在 `src/` + `grammar/` 全 0 命中，`grammar/core.ebnf` 67 条产生式里零元编程面。
   `[本次复算]` 见 一 B 组，全 0，逐项一致。因此八项里没有一项能在不先建这一层的前提下开始实施。

2. 八项里有 6 项落在同一条面上：对整张 HDFG 做全程序 / 不动点 / 同构级分析
   （13678 + 45 的验证面）。

3. 那条面 `[评估·实测]` 已是自编译成本的 72.7 %（30.0 s / 41.27 s），且已超线性
   （节点 ×1.98，因此分析面 ×4.71）。

因此不先把那条面修平，判什么都不可靠。所以本计划的第一段不是「实现功能」，
而是把地基修平、把测量协议立起来、重新测量。

注意：本档对第 3 条加了一条自己的限制（这是本计划与评估档最重要的差别）：

> `[本次复算]` 那个 72.7 % / ×4.71 的基线本身不可复现，同一二进制、同一语料、同一协议（min-of-3 / clean-cache / `nice -n 19`），

> 且本轮的数据违反单调性（`ccr`(20.79 s) < `cir`(25.34 s)，而 `ccr` ⊇ `cir` 的工作量）。
> 因此在协议修好之前，任何「修前 / 修后」的对比都不可能成立（没有稳定的「修前」）。
> 因此 S0 的第一步不是自证归因，是先把协议立起来（见 二）。

### 1.3 计时面不一致的性质（这一节是 S0.0 的存在理由）

`[本次复算]` 本次的 `bench2.json` 原始读数（min-of-3，逐条 clean-cache，`nice -n 19`）：

| 语料 | `check` | `cir` | `ccr` | loadavg |
|---|---|---|---|---|
| s500 | 0.303 | 0.805 | 1.204 | ≈12 |
| s1000 | 0.627 | 1.524 | 8.030 | ≈12 |
| s2000 | 1.142 | 25.336 | 20.791 | 12.5 |

三个不能忽略的事实：

1. 单调性被违反 `[本次复算]`：`ccr`(s2000) = 20.79 s < `cir`(s2000) = 25.34 s。
   而 `ccr` 的工作量严格包含 `cir` 的工作量（`main.cr`：`cir` 分支在 `df_state_finalize` 后提前 return，
   `ccr` 继续运行三个 pass + lower + save）。
   因此读数已经失去分辨它要测量的量的能力。这不是「噪声大」，是协议在该负载下失效。
   注意：评估的数据没有这个问题（它的 s2000 `ccr` 13.075 > `cir` 3.288），不能因此说本次的数据更差；
   只能说评估那三次采样恰好落在机器较空的窗口（见下条）。

2. 同一命令两次独立 min-of-3 差 7.7× `[本次复算]`：
   `s2000 cir` 评估 min = 3.288 s（样本 `3.288 / 11.290 / 21.318`）；
   本次评估的最小值 = 25.336 s（样本 `29.185 / 25.336 / 26.970`）。
   评估的 min 比本次评估的最小值 低 7.7×，且低于本次三次样本的最小值。
   因此 min-of-3 不足以在 loadavg ≈ 12 / 4 核的条件下取到真值。

3. 块序采样放大了变化 `[本次复算]`：`s1000 ccr` 样本 `9.538 / 8.030 / 17.190`，
   紧接着的 `s2000 cir` 块样本 `29.185 / 25.336 / 26.970`。
   同一块内的三次采样高度聚集，跨块的量级却跳变，因此变化在块间，不在块内。
   因此块序（block-sequential）采样是错的，必须交错（interleaved）。

因此对第 2.3 节那 30 s / 72.7 % 的处理（本档的正式立场）：
- `[推理]` 定性结论保留：分析面远贵于前端，且其增长远快于节点数，这一条在本轮同样成立甚至更极端
  （`cir` 在 1000 改为 2000 上 ×16.6，而 `check` 只 ×1.82）。
- `[推理]` 定量结论一律作废：`72.7 %`、`×4.71`、`≈30.0 s`、`41.27 s` 都不是可复用的常数。
  S0 必须先建立新基线，不得以旧基线做「修后」对比。

## 二、检查纪律（本计划的第一等交付物）

> 为什么检查纪律要单独成节、且排在 S0 之前：第 1.3 节已证「修前」读数是分布且分布跨会话不可比。
> 计量学上的常识：没有稳定基线的 A/B 对比不构成检查。所以协议本身是被交付的东西，不是脚注。

### 2.1 测量协议（计时类检查一律套用；不套用的计时读数一律不得引用）

| # | 规则 | 理由 / 出处 |
|---|---|---|
| P1 | `nice -n 19` 一律（硬性规则 6）。不得为了"测得准"而免 nice | 硬性规则 6；`canary_check.sh` 亦遵此（其 `CANARY_NO_NICE=1` 仅供自证/有效性检查用） |
| P2 | 逐采样 clean-cache（`rm -rf .core/cache`，相对 cwd） | `.cir` 缓存跨重建不失效 |
| P3 | 交错采样：`A,B,A,B,A,B,…`（不是 `A,A,A,B,B,B`） | `[本次复算]` 第 1.3 节事实 3，变化在块间 |
| P4 | N ≥ 5（评估与本档首轮都只用 3，不足以） | `[本次复算]` 第 1.3 节事实 2 |
| P5 | 每个采样记录 `loadavg`（采样前 + 采样后各一次） | 「不带负载的计时读数不可比」 |

### 3.3 S0.2，修法（在 S0.1 给出机制之后才硬编码）

候选机制（评估 `[推理]`，前提 = S0.1 证实）：`pa_in_unsafe` / `is_in_unsafe` 每次调用全扫所有区段，因此 `O(节点 × 区段)`。

`[本次复算]` 现成先例（同一文件里，评估实测的那条，本次逐字复核）：

```
src/compiler/region_check.cr:5-11
fn subgraph_containing(node_seq: int) -> int:
    // 显式映射：O(1) 归属查询（g_df_node_region 由 df_create_node 写入）
    if node_seq >= 0 && node_seq < g_df_node_count:
        return r64(g_df_node_region, node_seq * 8)
    return -1
```
- `g_df_node_region` 的写点唯一：`dataflow.cr:103` `w64(g_df_node_region, nid * 8, g_cur_sg);`（在 `df_create_node` 内，每节点一次）。
- 因此修法是「去掉每调用全扫」，不是发明新算法。

注意：一处必须先想清的语义差（评估未写，本档补）：
`subgraph_containing(n)` 返回的是最内层区段；而 `is_in_unsafe(n)` 要的是
「n 是否落在任一 `SG_UNSAFE` 区内」。二者不等价，
例如 `unsafe { if c { … } }` 里的节点，最内层是 `SG_IF`、但祖先里有 `SG_UNSAFE`。
因此修法必须是「取最内层 + 沿父链上溯」。

父链是现成的 `[本次复算]`：
- `dyn_arr.cr:150` `OFF_SG_PARENT : int = 24;  // parent subgraph index`
- `dataflow.cr:57`（`sg_push` 写 parent）、`:87`（`sg_pop` 恢复 `g_cur_sg`）
- 上溯先例（同文件）：`region_check.cr:70` `rc_releasing_region(alloc_node)`，
  `:68` 注逐字「分配点到最近一个「出口归还内存」的区域（含自身；沿 `OFF_SG_PARENT` 上溯）」
因此，因此 `[推理]` 修法 = `subgraph_containing` + 父链上溯，复杂度 `O(节点 × 嵌套深度)`；
嵌套深度由句法嵌套界定（远小于 `g_sg_count`）。

三处收敛为一份（`[本次复算]` 评估说「两份副本」，实际是三份，本档的更正）：

| # | 符号 | 文件：行 | 调用点 | 调用条件 |
|---|---|---|---|---|
| 1 | `pa_in_unsafe` | `ptr_analysis.cr:15-27` | `:201` | 逐节点无守卫 |
| 2 | `is_in_unsafe` | `region_check.cr:13-27` | `:200` | 逐节点无守卫 |
| 3 | `pv_is_in_unsafe` | `provenance_verify.cr:36-50` | `:64` | 有守卫（`op == IR_DEREF \|\| op == IR_STORE_PTR`） |

因此修法必须三处同改，且照本仓单源化先例（`#2026-09-20-1` 的「三条检查共用一份判定」，
`region_check.cr:29-56` 的头注逐字记录了那次收敛）收敛为一份，避免第四份副本再长出来。

Files：`src/compiler/region_check.cr`（落在哪一份待定，见下）· `src/compiler/ptr_analysis.cr` ·
`src/compiler/provenance_verify.cr` · `src/compiler/dataflow.cr`（若需新增 `subgraph_parent_of` 或类似原语）。
注意：这四档全在 `corec_files`（`[本次复算]` `build_selfhost_native.py:349-351`、`:360`）
因此只影响 `corec`，不进 `corearch`。
注意：自源即语料：这四档本身是 `check` 作业的语料（`src/ci/run.sh:71-75` 的 `check_compiler_sources`）
因此新增/改动代码里任一条诊断即 rc=1，故新代码不得引入新的诊断面。

检查（两向断言，缺一不可）：

| 向 | 检查 | 怎么运行 |
|---|---|---|
| 正向 | 同会话（P3 交错、N≥5）下，（a） `(ccr−check)/check` 在 s1000 与 s2000 上都下降；（b） S0.1(2) 的迭代计数从 `O(节点×区段)` 降到 `O(节点×深度)`（这是主要检查，它不受负载影响）；（c） 规模曲线相邻点局部幂次 ≤1.3 | 本地；P11，因此不进 CI |
| 反向断言 | 把修法改回原样，计时/计数必须回升到原量级。做法：保留一份全扫版本，用一个编译期常量开关（或直接改回 `loop { if si >= g_sg_count …}`）对比；计数检查必须精确回到 `2.588×10⁹` 量级（±20 %） | 同上。注意：见下 |
| 零影响（字节面） | 同一个源的 pre/post，固定语料的 `.ccr` 逐字节相同；canary ELF 5/5 值不变 | `bash tools/baseline/canary_check.sh` + `parity_run.sh`（进 CI 的 `selfhost-tests`） |

注意：反向断言的一个陷阱（本档必须写，否则这条检查会误报通过）：
改回原样会让 `corec` 二进制变（源码变），因此凡把 `corec` 二进制本身当定位点的检查都会失败。
因此反向断言的定位点必须是「计数」与「同会话比值」，不能是二进制 sha；
字节面检查的定位点必须是「产物」（`.ccr` / ELF），不能是二进制（先例：`docs/superpowers/specs/2026-09-20-mapping-docs-scope-boundary` 一脉的
「输入定位点别固定编译器二进制」纪律）。

零影响检查的非真空证据（必做，否则「没变」是自述句）：
1. 证明它会失败：做一个故意改语义的对照突变（例：把 `SG_UNSAFE` 判定改成恒 `0`）
   因此 `region_check` 会报出本被抑制的 `EC_B_LIFETIME`(B011)，因此语料 rc=1 / 产物变，因此字节面检查立即失败。
   因此这条证明「该检查能分辨语义变化」。
2. 证明它在该改法下真不变：S0.2 的修法下，字节面检查通过，且同时 `#2026-09-20-1` 的
   `test_region_escape.py`（15 例）全部通过、`B011` 的正/反两向断言（正向 7 条 + 反向对照 7 条）全部通过。
   注意：这两条必须同批给，只有 1 说明检查能失败，只有 2 说明没失败，合起来才是"等价改写"的证据。
3. 突变控制按本仓既有纪律：突变只运行在临时副本上并当批撤销（突变控制是本仓回归检查的既有成分，
   见 CLAUDE.md「行为探针 + 突变控制 + 三态纪律」）。
