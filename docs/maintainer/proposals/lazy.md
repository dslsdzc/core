# Core 惰性求值

> 定位：受众 = 维护者/贡献者；状态 = 部分实现。图具有惰性的论点成立，eager 是当前策略；调用级 thunk 仍是 eager 兼容形态；控制流级第一切片（纯标量调用，含常量/未重写值实参，下沉到唯一 if/loop 条件 force 点）已实现；可变实参/alloc/跨迭代 hoist 未做。

## 设计原则

- 图本身具有惰性：节点不在边上游等待时就不执行。当前 IR 生成策略是 eager：节点一出现就执行。这是策略选择，不是图的限制。

## 自动惰性推导

编译器检查图，决定一个节点是否需要惰性求值：

```core
result := if cond:
    expensive1()     // 只在 cond=true 时用到
else:
    0                // cond=false 时到这里
print(result)
```

| 条件 | 策略 |
|------|------|
| 节点结果只用在一个分支里 | 延迟到确定需要时执行 |
| 节点有副作用（IO、文件、volatile） | 永远 eager，不惰性 |
| 节点在循环体内且每次都用 | eager |
| 节点在循环体内但条件性使用 | 惰性 |

## 无关键字

惰性推导与此前的指针验证、编译期求值、概率推导一致：由编译器检查图并自动完成，不引入 `lazy` 关键字。

```core
x := expensive()       // 编译器自动选择 eager 或 lazy
y := cond ? x : 0      // 如果 x 只用在这里且无副作用，就自动惰性
```

## 副作用标记

编译器需要知道哪些节点有副作用。纯函数的调用自动可惰性。副作用的标记来源：

| 来源 | 判定 |
|------|------|
| 纯函数（无 IO、无变异） | 可惰性 |
| IO 操作（read_file、print） | 不可惰性 |
| volatile 内存操作 | 不可惰性 |
| FFI 调用 | 默认不可惰性 |

## 惰性节点被多处使用

```core
x := expensive()   // 编译器决定惰性
y := cond ? x : 0
z := x + 1         // x 这里也被用了，必须求值
```

如果编译器发现标注为惰性的节点实际有多条路径需要它，就自动升级为 eager，用户不需要感知。

## 惰性对语义无影响

无论编译器选择惰性还是 eager，程序输出一致。惰性只是策略选择，不影响正确性。

当前核实的两点：

- THUNK/FORCE 当前只是值传递：`IR_CALL` 在 THUNK 前已经急切发射，ELF/interp 均按值传递降级，没有实际延迟。
- `use_count <= 1` 判定存在时序问题：`compute_usage_counts()` 在全部 ir_gen 之后运行，判定时读到的恒为 0 或未初始化，“单次使用”条件实际不生效。

更新（2026-08-08）：惰性求值已部分实现，范围为调用级（文档设计的子集）：

已实现：
- IR 指令 `IR_LAZY_THUNK(46)` / `IR_LAZY_FORCE(47)`（ast.cr）
