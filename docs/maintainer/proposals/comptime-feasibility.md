### 2.3 规模曲线 —— **这是本档最重要的一张表** `[实测]`

语料 = 脚本合成的 N 个函数（每函数 6 条语句，形状一致，`/tmp/ctfeas/scale/s*.cr`）。
`check` = 只跑前端；`cir` = 前端 + `df_state_finalize`；`ccr` = 前端 + `df_state_finalize` + 三个常开 pass + `lower` + `save`。
**min-of-3，clean-cache，nice -n 19。**

| 语料 | NOD 节点数 | REG 区段数 | `check` | `cir` | `ccr` | `ccr−check`（分析面） |
|---|---|---|---|---|---|---|
| s1000 | 77,270 | 1,086 | 0.525 s | 1.514 s | **3.063 s** | 2.538 s |
| s2000 | 153,270 | 2,086 | 1.109 s | 3.288 s | **13.075 s** | 11.966 s |
| 比率（×1.98 节点） | | | **×2.11** | ×2.17 | **×4.27** | **×4.71** |
| **真负载** `src/compiler/main.cr` | **169,418** | **7,638** | 4.96 s | — | **41.27 s** | **≈30.0 s** |

**读出来的三件事：**

1. `[实测]` **前端是线性的**。`check` 在 250/500/1000/2000/4000 五个点上是 0.135/0.271/0.539/1.103/2.443 s
   ——**逐点严格 ×2.0**（×16 输入 ⇒ ×18.1 时间）。
2. `[实测]` **`ccr` 的分析面是超线性的**。节点 ×1.98 ⇒ 分析面 ×4.71（**局部幂次 ≈ 2.2**）。
   单次采样在 s500 上另得：39,270 节点 ⇒ 分析面 ≈0.86 s；三点幂次 1.58 → 2.24 **本身在增长**
   ⇒ **不是干净的单项幂律**。
3. `[实测]` **真负载比合成语料更糟**：真负载节点数只比 s2000 多 10.5 %，分析面却贵 2.5×；
   其 REG 区段数是 s2000 的 **3.66×**（7,638 vs 2,086）。

**机制候选** `[推理]`（**不是实测归因**——我无法在不改源码的前提下逐 pass 计时）：

- `src/compiler/ptr_analysis.cr:15-29` 的 `pa_in_unsafe(node_seq)` **每次调用全扫 `g_sg_count` 个区段**。
- `src/compiler/region_check.cr:15-29` 的 `is_in_unsafe(node_seq)` **逐字同样的全扫**（两份副本）。
- ⇒ 两处皆 **O(nodes × regions)**。
- **本仓自己的文档已记过这条**：`docs/maintainer/design/execution-mapping-design.md:1152` 逐字
  「⚠ 且 `pa_in_unsafe()`（`ptr_analysis.cr:15-30`）**每次调用都全扫 `g_sg_count` 个 SG**——O(SG) per node，
  **已被 QC 化为 O(nodes × SGs)**。」
- 对照：同文件 `region_check.cr:5-11` 的 `subgraph_containing()` **已经用了 O(1) 显式映射**
  （`g_df_node_region`）——**O(1) 的修法在同一文件里就有先例，只是没落到 unsafe 判定上。**

**⇒ 对本评估的直接后果** `[推理]`：
任何"让编译器对程序图做更多分析"的方向（本批 15 个方向里**绝大多数**），都是在**已经超线性、
且已占 73 % 编译时间**的那个面上加工作。**这是本档的核心约束。**

### 5.4 【独立小节】Partial Evaluation + Binding-Time Analysis

**复杂度落在哪** `[推理]`：

BTA 是对**绑定时间格**（`{Static, Dynamic}` 或含 `⊥` 的三点格）求**不动点**。传播沿
**def-use 边 + state 边 + 调用图**。本仓的规模量（`[实测]`）：
**169,418 节点 · 156,217 边 · 7,638 区段 · 15,244 调用点**。

工作集估算 `[推理]`：每个节点一个绑定时间（1 byte）+ 每边一个传播记录 ⇒ **最小 0.5–1 MB 级**，
相对现有 41.7 MiB 的 `.cir` 缓存不算大。**问题不是内存，是迭代次数**：
调用图为环（`[实测]` 编译器自身是递归的——`sq`/`gen_expr`/`checker` 全有自递归），
⇒ 不动点迭代 **≥ 调用图 SCC 数 × 图规模**。

**落在哪个成本面上** `[实测 → 推理]`：这是 **O(nodes × iter)** 或 **O(edges × iter)** 的遍历，
**与 §2.3 里已经占 30 s 且超线性的 `ptr_analysis`/`region_check` 是同一形状**。
⇒ 自然落点不是"41 s 变成 60 s"，而是**那 30 s 变成 30 s × k**，k = 迭代数。

**⇒ 编译器自己的 38 个文件里有没有会因此爆炸的形态？** `[实测 + 推理]`

**有，而且量出来了：**

| 形态 | `[实测]` | `[推理]` 对 PE/BTA 的意义 |
|---|---|---|
| **大函数**（HDFG 单函数级） | 最大单函数快照 2.63 MB（`type_selftest_run`）· 1.56 MB（`gen_expr`）· 1.11 MB（`infer_expr`） | 不动点在**函数内**先跑；这三个函数的图规模是 p50 的 **63×–105×** |
| **巨型平坦函数** | `[实测]` `.cir` 缓存 **top 100 函数 = 43.3 % 字节**；p50 25 KB vs max 2.63 MB（**105× 长尾**） | 预算/超时策略必须按**函数**而不是全局设，否则长尾函数单独撞顶 |
| **递归 + 互递归** | `[实测]` 调用点 15,244；`checker`/`ir_gen`/`parser` 互为环 | 不动点迭代数 = SCC 深度，**不可预知** |
| **thunk/force 脚手架** | `[实测]` 24,215 节点 = **14.3 %** 是 `IR_LAZY_THUNK`/`IR_LAZY_FORCE` | 绑定时间必须**穿透**这层包装，否则每个 thunk 都是一个伪"动态"点 ⇒ **PE 收益被自己的脚手架吃掉** |
| **结构性节点** | `[实测]` **40.8 %** 是 LABEL/JUMP/BRANCH/THUNK/FORCE/ARENA_* | residual graph 复制时**全部跟着复制** |
| **类型项覆盖不足** | `[实测]` 只有 **36.09 %** 节点带项 | 「这个子图可执行」的判定需要类型信息；**64 % 的节点上判不了** |

**判定**：❌ **不可行（当前）**。
**不是因为方向错，是因为三条同时成立**：
① 前置（编译期求值器）**为 0**；② 落点面**已超线性且已占 73 % 编译时间**；
③ 不动点迭代数**在本仓语料上不可预估**（递归 + 长尾）。

**最小可行切片（若维护者仍想推进）** `[推理]`：
先做 **"单函数内、无调用、无环"的 BTA**（即今天的 `#check` 折叠器 + 局部变量传播），
**且必须有预算上限**。这一步的判据可以完全复用 `#check` 的 V01/V05/V06 三态机制。

### 5.5 【独立小节】Polyvariant specialization —— 代码膨胀的量级

**这是它最著名的问题，本仓的数字尤其不利。**

**膨胀来源一：连骨架一起复制** `[实测]`
编译器自身图的 **40.8 %** 是结构性节点、**14.3 %** 是 thunk/force。
⇒ **一个"语义上只有 55 条指令"的函数，复制一份实际要复制 ~93 个节点。**

**膨胀来源二：变体基数** `[实测]`
`IR_CALL` = **15,244** 个调用点（编译器自身）。每个调用点若按 N 个静态值分裂 ⇒
**最坏 15,244 × N 个变体**。对照：现有 monomorphization 只在**泛型**上做，
`[实测]` 其例子是 1 → 2（`plans/2026-09-11-r2-p3-capabilities.md:443`），且 `.ccr` 只涨 **+370 B**。
**polyvariant 把它推广到"任何静态关系" ⇒ 基数从"泛型实例数"放大到"调用点数 × 静态值域"。**

**膨胀来源三：缓存本身变成 O(N) 查找** `[实测]`
`monomorph.cr:780-793` 的 `gen_find_cached` 是**线性扫描 + intern 串比较**。
今天实例少（`[推理]` 数十量级）没问题；变体上到**千/万**量级时，
**每一次查缓存是 O(N)** ⇒ 总成本 **O(N²)** ——**又叠在 §2.3 的已超线性面上。**

**膨胀来源四：产物侧** `[实测]`
`.ccr` 12,698,096 B 对应 169,418 节点。**若变体使节点数 ×3 ⇒ `.ccr` ≈ 38 MB**，
`corearch` 要吃它（`[实测]` 今天 4.91 s）。而 `.cir` 缓存已经是 **41.7 MiB**，
**底层 1 GiB bump 堆、零回收**（`rt.s:15-17`）——`cir_cache.cr:505-521` 已记录过一次因此的 OOM/SIGSEGV。

**缓解手段与代价**：

| 手段 | 代价 |
|---|---|
| 变体上限（数量/深度） | 撞顶时的语义 = ？本仓禁止静默降级 ⇒ 必须硬错（新错误类） |
| 只对显式标注的函数特化 | 退回 Zig 语义，削掉"自动"卖点 |
| 变体去重 | 需**节点身份**（现无，只有下标） |
| 惰性/按需 | 编译期节省、运行期付费；且**与"编译期成本可预测"冲突** |

**判定**：❌ **不可行（当前）**。
**膨胀不是"可能会有的风险"，是在本仓已量出的三个数字（40.8 % / 15.3K / O(N) 查找）上直接相乘。**

### 5.6 【独立小节】Proof-directed comptime —— 编译期 SMT

**时间尺度** `[推理]`：SMT 求解是**毫秒→秒→分钟**级（取决于理论与目标），
而本仓的**全量构建 = 15.2 s**（§2.1）、**一次自编译 = 41.3 s**（§2.2）。
⇒ **一个目标的 SMT 超时（常见默认 10–30 s）就吃掉一次完整自编译。**
**⇒ 数量级直接冲突，不是调优问题。**

**CIC + SMT 现状（team-lead 要求我**自己再核一遍**）** `[实测]`：

### 5.7 【独立小节】Typed HDFG fragment 作第一等 comptime 值

**与 `.cir` / `.ccr` / V8 的关系** `[实测 + 推理]`：

### 5.8 【独立小节】Semantic reflection / whole-program query

**全程序查询在编译期执行的代价** `[实测]`：

- **本仓有过一次同类的错误，并被逐字记录**：`.cir` 快照曾把**全程序边表/字符串表**随**每个函数**落盘
  ——`cir_cache.cr:406-410` 逐字：「实测 **4,314 万条边记录 vs 20.6 万节点记录**」
  「它正是本条二次膨胀的**起点**」。修法（v20）是**收窄到本函数**。
- `[实测]` 今天的规模：**6,238 串 / 156,217 边 / 169,418 节点 / 7,638 区段**。
  **"全程序查询"在这个规模上是 O(全图) per query**；若无索引，**N 次查询 = O(N × 全图)**。
- `[实测]` 查询所需的语义事实**大部分已存在**（`g_sgs` 区段表 · `g_df_edges` 的
  `kind=1` state 边 · `g_type_terms` 类型项 · `g_gen_instances` 泛型实例表 ·
  `func_ispure` 纯度位）——**缺的是查询 API 与索引，不是数据**。

**判定**：⚠ **有条件可行**。**条件**：
① 查询必须是**离线/汇总**的（一次遍历产出索引），不是每次从零扫；
② 判据必须带**成本测量**（本仓已有先例：`docs/superpowers/plans/2026-09-11-effect-purity-fix.md:100`
   「**风险**：① `find_func` O(F²)（大项目下变慢——**可先测编译耗时，超阈值再换哈希**）」）；
③ 类型项覆盖面须先从 **36.09 %** 提到足以支撑查询语义的水平（否则查询结果**静默缺格**——
   本仓对静默零容忍）。

## 六、总体判定

### 6.0 一句话

> **方向没错，但它今天不是"要不要做"的问题，是"地基是空的 + 速度面已经超线性"的问题。**
> `[实测]` comptime 的**自动推导**（提案的第一原则）实现度 **0**；`@comptime` 是空壳；
> 唯一的编译期求值是 `#check` 的**字面量折叠器**。同时 `[实测]` 自编译 **41.3 s** 里
> **30.0 s（72.7 %）花在常开的 HDFG 分析 pass** 上，而这个面**已实测超线性**
> （节点 ×1.98 ⇒ ×4.71）。**本批 15 个方向里，需要"在图上多做分析/多复制图"的那些，
> 全部落在这个面上。**

### 6.1 哪些方向**现在就能做**（不依赖未落地的东西）

按前置多少排序（**越靠前越可做**）：

### 8.3 ②（全程序查询）与 ⑥（equality saturation）的成本量级 `[推理]`

- `[推理]` **无索引 ⇒ 每次查询 O(全图)**；N 次查询 ⇒ O(N × 全图)。**量级 = ×1.5–×3**，
  且要为索引付一次全图遍历（又一次落在 §2.3 的超线性面上）。

**⑥equality saturation：**

- `[推理]` 饱和 = 在带等价类的图上跑**不动点**；e-graph 大小**无先验上界**（这是该技术最著名的

  同一条已超线性面上的不动点**。分母不是 41 s，是那 **30 s × 迭代数**。

| **⑦** 多 stage（target-bind / load / JIT） | **编译速度**：每 stage ≈ 一次完整编译（`[实测]` 41.27 s 冷）；且 `[实测]` 该三项**在本仓零实现** |

### 9.4 **八项之外，但必须先做的一件事** `[推理]`

> 八项里有 **6 项**（①③⑥⑦⑧ + ④⑤ 的验证面）的落点都在**同一个面上**：对整张 HDFG 做
> **全程序 / 不动点 / 同构**级分析。而 `[实测]` 那个面**今天已经是自编译成本的 72.7 % 且已超线性**。
> **⇒ 无论最终做哪几项，§6.4 的 S0（把 `pa_in_unsafe`/`is_in_unsafe` 改 O(1)）都是前置中的前置。**
