## 1. 核心抽象

Core 将一切执行抽象为HDFG。
程序员编写顺序的函数调用与并发启动，编译器自动构建并优化对应的HDFG。

| 编程概念 | HDFG映射 |
|----------|--------------|
| 函数 `fn f(x) -> y` | 计算节点（从输入边到输出边） |
| 函数调用 `f(a)` | 节点实例化，参数作为输入令牌 |
| `return x` 或 `yield x` | 产生输出令牌 |
| `go f()` | 创建新的执行流节点，立即返回数据流句柄 |
| `await handle` | 显式同步边：等待上游节点产出值 |
| `recv()` | 从通道/流接收数据令牌，触发节点激活 |
| 循环 `for` / `loop` | 扇出/扇入拓扑的生成器 |
| 分支 `if` / `match` | 选择路由（有条件的数据转发） |
| `flow` 声明 | 持续运行的节点（有状态，可多次激活） |

关键性质：

- 执行顺序由数据可用性驱动，而非文本顺序。
- 显式并发与 HDFG 统一表达。

## 2. 静态与动态HDFG

### 2.1 静态图

编译时已知：函数调用关系、模块连接。
等价于传统的数据流程序图。

```core
fn transform(x: int) -> int { x * 2 }
fn display(v: int) { println(v); }

fn main() {
    data := [1, 2, 3];
    for d in data {
        go display(transform(d));
    }
}
```

图结构：data → transform 节点（多个实例） → display 节点（多个实例）。
for 展开为扇出，go 为每个实例创建执行流节点。

### 2.2 动态图

运行时图拓扑可变：产生新节点、删除节点、重新连线。
这是 Core 应对长期运行服务和自适应系统的关键能力。

```core
flow load_balancer() {
    loop {
        select {
            req: Request = recv => {
                worker := go handle_request();
                worker.send(req);
            }
            signal: HealthCheck = recv from monitor => {
                signal.target.terminate();
            }
        }
    }
}
```

load_balancer 节点不断创建/移除 worker 节点，HDFG在运行时动态演化。

## 3. 执行流与数据流节点的统一视图

一个 flow 实例既是：

- 执行流：拥有自己的栈和指令指针。
- 数据流节点：通过 recv 消费输入，通过 yield 或 return 产出输出。
- 图中的顶点：可以连接到其他节点（通道/句柄）。

这种统一性使得：

- 并发推理无需关心线程/协程的底层差异。
- 静态分析工具可以提取完整的数据依赖图用于形式化验证。

## 4. 语法元素到图元件的映射

| 语法元素 | 图语义 | 激活条件 |
|----------|--------|----------|
| `fn f(in) -> out` | 有向无环子图，输入边->节点->输出边 | 调用时实例化 |
| `go f(args)` | 新建执行流节点，边连接实参到形参 | 立即激活 |
| `x := f(args)` | 创建临时节点，当前执行流挂起等待结果 | 等待输出令牌 |
| `yield value` | 向当前流句柄发送输出令牌 | 消费方 recv 时激活 |
| `recv()` | 等待输入令牌到达，激活节点 | 令牌到达 |
| `select { ... }` | 多输入汇合点，任一输入到达即激活对应分支 | 最早到达的令牌 |
| `chan.send(v)` / `chan.recv()` | 通过通道连接节点，形成数据边 | 边界匹配 |
| `for x in source` | 扇出：source 产生序列，每次迭代产生新节点实例 | 迭代时 |
| `loop { ... }` | 自环反馈结构，节点激活后可再次激活 | 内部 yield/recv |

## 5. 并行计算 π 的图表示例

```core
flow worker(id, base, chunk) -> dex {
    loop {
        partial := leibniz_partial(offset, chunk);
        yield partial;
        offset += chunk * num_workers();
    }
}

flow orchestrator(workers, chunk_size) {
    flows : ., mut = [go worker(...), ...];   // 扇出多个 worker 节点
    loop {
        for f in &flows {
            pi += 4.0 * f.recv();           // 扇入：从每个 worker 收集部分和
        }
        println(pi);
    }
}

fn main() {
    go orchestrator(8, 10000);
}
```

图结构：

- 8 个 worker 节点，每个独立运行，产出 dex 令牌。
- orchestrator 节点通过 recv() 从 8 条边收集令牌，累加后输出。
- 所有边是缓冲通道，允许生产者/消费者异步执行。
- 循环构成反馈：worker 每次 yield 后继续计算下一块。

## 6. 形式化验证视角

从这张HDFG可以直接导出：

- 数据依赖：边定义了节点间的偏序关系。
- 吞吐量/延迟分析：节点执行时间 + 通道缓冲。
- 无死锁证明：若图无环且缓冲合理，则无死锁。
- 功能规约：可将每个节点的 requires/ensures 组合，验证整体管道正确性。

---

## 7. 与硬件执行模型的映射

Core 的HDFG可以高效映射到多种底层硬件：

- 多核 CPU：节点映射为线程/协程，边用无锁队列或共享内存。
- GPU：节点映射为 kernel，边映射为 global memory + 同步。
- 分布式：节点映射为远程执行器，边映射为网络消息。
- 无 MMU 嵌入式：节点与边静态分配，无动态分配。

语言自身不规定映射策略，由后端根据目标平台决定。

## 结论

Core 的 HDFG 将并发原语（go、await、flow、recv、yield）统一为图结构——同一张图同时服务于运行时调度、编译期分析和形式化验证。

## 7. 指针安全

HDFG的另一个消费端是指针安全验证。图中每个值的出生节点记录了它的来源（provenance）。

```
ALLOC(arr[16]) ──→ ADDR(&arr[0]) ──→ ADD(p + n) ──→ DEREF(*p)
                      ↓                  ↓              ↓
                  provenance=arr    offset=n       验证 offset < 16
```

编译器在 DEREF 节点处自动验证当前偏移是否在分配范围内。从 ALLOC 到 DEREF 的路径就是安全证明。不需要 borrow checker、Arena tag、或 RawRef 等额外概念。详见 `docs/maintainer/design/pointer-model.md`。

## 8. 环语义标注：迭代与一致解（非因果范式准备）

图上的环有两种语义，由语义标注区分：

```
ITER  = 迭代语义（现状）：SG_LOOP——因果循环，每圈发生在后一圈之前（时间序）
FIXPT = 一致解语义（非因果环）：环上算子的不动点——值使环自洽，不迭代执行
```

- **FIXPT 语义 = 图上的 μ/ν 算子**（Knaster-Tarski 最小/最大不动点）——验证内核既有理论（W-类型/不动点）的图落地，非新理论
- **验证契约**：不动点性质——「此值是不动点」可证书核验（契合证书内核：计算在外、健全性在内）
- **执行**：FIXPT 环无当前后端（计算不动点 PSPACE 难）——区域是声明性的（语义定义，执行后置，同规约层）
- **设计依据**：Deutsch CTC 一致性条件（1991）、非因果图灵机（arXiv 1601.06522）——非因果计算的图描述标准形态 = 环 + 不动点语义
- 未来范式的建模细节不在本文档范围——本节的唯一职责是让图框架今天就能描述非因果结构（语义标注已定义，映射表未来接入）

### 超图灵预留接口（描述可、执行未知、验证例外）

超图灵计算（图灵可计算以上）的描述接口——**结构零新增**，接口 = 标注空间的文档化开放：

```
神谕节点  = 节点 + 任意决策函数标注（Turing 1939 oracle——「此节点计算函数 F」，
           F 可以不可计算；跳变层级 ∅ < ∅′ < ∅″…）
超限循环  = FIXPT 标注的序数深度（ITTM，Hamkins-Lewis 2000——序数时间计算，
           极限阶段 limsup 规则；Γ^α 序数迭代——不动点理论已有此深度）
连续节点  = 实数语义标注（BSS 机器，Blum-Shub-Smale 1989——精确实算术，
           无限精度实数节点）
```

- **执行层**：物理问题，不在框架职责内（Zeno 机器能量发散、BSS 无限精度不可验证、ITTM 为超任务——物理可实现性未证实，Cotogno 系列批判）
- **验证层**：神谕节点不可验证——例外入口（与 unsafe 同层）；验证侧对应物 = ω-规则（内核理论已预埋）
- 预留接口的唯一职责：标注空间今天就能描述超图灵结构（神谕/超限/连续），执行与验证按层分配

### 模糊语义标注（FUZZY——格值隶属度）

```
FUZZY 标注 = {
  图结构：通用形状 + 软分支（加权融合菱形——IF 不二分，
          两路都执行，按隶属度加权融合）
  语义定义：格值隶属度 [0,1] + t-范数/余范数/蕴涵
          （剩余格代数——Lukasiewicz / Gödel / Product 三种基本 t-范数逻辑，
           Hájek BL-代数系）
  验证契约：分级蕴涵——「公式以程度 d 成立」——定量验证（非二元）
  执行映射：dex/apx 数值实现（[0,1] 精确小数或近似授权）
}
```

- **与概率的边界**：概率是可加测度（测度论），模糊是格值隶属度（格论，min/max 结构）——两个独立语义
- **无专属硬件**：历史模糊芯片（Fujitsu/Togai，80-90 年代）已消亡；模糊无物理动机（对比量子/模拟），执行 = 通用设备软件实现——同概率先例（语义标注的价值不依赖专属硬件，模糊控制/推理程序在通用 CPU 上运行）
- **存储侧对应（2026-08-27 v4）**：本节不可重算标注（FIXPT / 神谕 / BSS / 模糊融合）= **图内无配方条目**——统一规则见 `docs/academic/cache-semantics.md` 条款 4b（必须有 home、驱逐必写回、身份 = 图节点；不按范式枚举）；映射实例侧（寄存器分配 = 缓存语义映射实例）见 `docs/maintainer/design/regalloc-cache-mapping.md` §三

### 共归纳/非良基语义（CORE 标注——已存在的范式，非预留）

**定位：这不是预留接口——是今天所有数字硬件的语义。** 每一块同步数字电路都是余归纳流机器（时钟 = 流步）；工业先例 Lustre/SCADE（A380 飞控、地铁信号、DO-178C 认证）的语义 = 余归纳流；Vélus 验证编译器（Rocq 余归纳流 → CompCert → 汇编，机器核验）。

```
CORE 标注 = {
  图结构：环 + ν（最大不动点）语义——FIXPT 的 ν 侧
  语义定义：终余代数（流 = F X = D×X 的终余代数）；
          双相似 = 观察等价（共归纳外延性）；
          非良基集合（Aczel AFA——超集 Ω = {Ω}，
          典范模型 Vc = 可及点图的商——非良基集合就是图模双相似）；
          保护递归（▷ 算子 + Löb 不动点——生产率保证）
  验证契约：共归纳可验证——双相似证明（内核 ν 机制）；
          保护递归使每个有限前缀有限时间可算——良基的（余代数意义），
          不是例外入口（与超图灵不同）
  执行映射：存在——同步硬件 / SCADE / 数据流加速器（原生）
}
```

**与既有框架的衔接**：
- I/O 转导器（平台抽象：程序 = 流转导器）就是 `CoNode (S→T×S)×S`——I/O 抽象已是共归纳语义
- FIXPT 的 ν 侧（最大不动点/双相似）已在环语义标注中预埋
- 验证内核的终余代数/W-类型对偶（ν 机制）——共归纳验证直接可用
